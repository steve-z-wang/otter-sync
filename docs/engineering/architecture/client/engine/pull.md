# Pull

## 1. Introduction and Goals

Pull applies what the server says about records. A page covers every channel the client follows; each change in it is the full state of one record with a *stamp*. Pull keeps two orders straight at once: each channel's cursor moves only by whole pages, and content for a record applies in stamp order no matter which path delivered it. A change that cannot be applied fails alone and is reported, never silently skipped.

## 3. Context and Scope

Pages come from two paths and go through one gate:

| Path | Entry | Result |
| --- | --- | --- |
| HTTP catch-up or WebSocket frame, via the downlink worker | `receive_downlink(page, request?)` | `DownlinkProgress {disposition: covered/recover/applied, gaps, continues, report}` |
| Direct callers (tests, simulation) | `apply_page(page)` | `ApplyReport {applied, stale, cursors, reports}` |
| A bounded historical page of one Scope's interval | `apply_bootstrap_page(scope, subscription_id, run, after, page)` | `BootstrapApply {Stale / Failed / Applied}` with the same `ApplyReport` |

`downlink_request()` builds the one request for every initialized subscription (`None` when none is). Pull owns the ledger: `axton_subscription` (channel → subscription identity, starting cursor, cursor, and the same row's bootstrap half; the delivery cursors are null until a first delivery boundary is committed, so a subscription without one asks for nothing) and `axton_record` (the stamp last applied per record, retained across deletion and unsubscription). It writes records through the authority applier shared with [Settlement](settlement.md); the only queue state it touches is the *diverged* mark on a mutation whose replay failed.

## 5. Building Block View

- **Channel gate, per channel.** A channel the client does not follow is ignored (a pull still in flight when the user unsubscribed cannot re-subscribe); a channel whose range ends at or before the local cursor is covered; a channel whose range starts beyond the local cursor is a gap. A gap on any channel means the page is not applied at all: `receive_downlink` reports `recover` and names the channels, `apply_page` returns an error.
- **Subscription epoch.** The client counts, in memory, how many times each channel's subscription changed since open, and remembers the pull it issued with those epochs. A page answering a pull from an earlier epoch was built against a cursor the resubscribe reset; it is stale before the gap test.
- **Stamp comparison.** Per record: a newer stamp applies (beneath pending operations or into the visible row); an older one is ignored; an equal one with equal content rewrites nothing, and with different content is a *conflict* report. A newer deletion removes the row and keeps its stamp; declared descendants are deleted locally without rewriting their own stamps.
- **Reports** (`Report {kind, model, identity, stamp, code?, ordinal?}`): `readFailed` for a change the server could not read (`error` set; nothing written), `skipped` for a state this client's schema refuses (nothing written), `conflict` for equal-stamp different content (nothing written), `diverged` for a pending operation that no longer replays over the new base (the base is visible; the operation stays queued, is still sent and is marked `diverged` in `record_status` until it completes or is rejected).
- **No ownership.** A channel is a delivery path; unsubscribing deletes the subscription row only.
- **Bootstrap pages are not gated by the delivery cursor** ([#151](https://github.com/zanminwang/axton/issues/151)). A historical page covers `(B, S]`, an interval entirely at or below the delivery cursor's origin, so the channel gate above would call it *covered* and apply nothing. It is therefore not applied through that gate at all: its own fence is the subscription identity, the run, the stored progress `B` and the echoed channel, origin and `from`. A response that fails any of those is `Stale` and writes nothing - which is how a page that survived an unsubscribe, a retry, a reopen or a rebuild cannot recreate the task it answered. What it does *not* bypass is the stamp comparison: every record it carries goes through the same applier, so a historical record older than what delivery already applied is ignored, an equal one is idempotent, and a newer deletion it arrives after is not resurrected. `bootstrap_cursor` and the delivery `cursor` move independently and neither writes the other.
- **A historical page's failure is the run's, not the channel's.** A `readFailed`, `skipped` or `conflict` report on a historical page leaves the page's successful authority committed, does not move `bootstrap_cursor`, and fails the run until an explicit retry (which revisits the same `after`); a `diverged` replay is reported without failing it. An ordinary page instead advances its cursor past such a record, because delivery must not stall on one record (D7).

## 6. Runtime View

A page is one SQLite transaction: gate every channel; merge all membership evidence, admit positive bodies and apply authority by stamp, release final unheld bases, collecting reports; rebuild the records that hold a base once; move every gated-through channel's cursor to its `to`; commit. With a registered `onStore` Model, reversible preparation selects only incoming newer-stamp upserts (full row and identity) and deletes (identity) that passed preflight. The callback reads the pre-store local view plus its own transaction writes. No callback runs for older, same or conflicting stamps, known invalid records, local cascades or optimistic replay. Accepted occurrences keep their incoming order within each Model; Models run in schema-name order. Channel Page and Bootstrap validation rejects duplicate Channel/record pairs; a shared identity can occur in several Channels. The internal occurrence journal also handles decoded direct authority; it does not change that wire rule ([Frontend interface](../frontend-interface.md#6-runtime-view)). A crash before commit leaves the cursors where they were, and the re-pulled page applies idempotently by stamp. A page never completes a push; that is the receipt's job ([Settlement](settlement.md)). The reports go back to the caller; the downlink worker hands them to the application ([Downlink worker](../connection/controller/downlink-worker.md)).

A historical page is one transaction too: re-read the row and refuse the response unless it still answers the stored task, apply its records by stamp, and then either commit a known preflight record failure with the successful authority and hooks but unchanged historical progress, or move `bootstrap_cursor` to the page's `to`. A callback failure rolls the page back, then records the failed run in a separate identity/run-guarded transaction; failed bookkeeping is retained for retry. A genuine post-hook storage failure instead retains the admitted page for local retry. If a hook unsubscribes its own Channel, admitted authority still stores, but the old cursor, run and observers cannot update a new same-name registration. The page that reaches `S` also stores the channel head it observed as the run's fixed completion barrier `H`, and completes the run in that same transaction when delivery is already at or past `H`; otherwise the run waits, and the transaction that later moves delivery to `H` completes it. Nothing refreshes `H` while the run waits, and bootstrap never advances the delivery cursor itself.

## 9. Architecture Decisions

**Membership release and subscription lifetime are separate.** A durable holding ledger merges upsert/remove evidence and enrollment claims per Channel/record. Last-hold release evicts replicated content while retaining stamp/absence evidence and local work. Unsubscribe still removes only registration/progress and retains holds/content. Authoritative null retains its cascade semantics.

**One applier for every path.** A page change and a receipt record are the same authority, and the same function stages them ([Settlement §9](settlement.md#9-architecture-decisions)).

**A page is one unit ([#95](https://github.com/zanminwang/axton/issues/95)).** Each event carries a membership cursor, but polling still moves only to a whole page's end. Evidence, body admission, release and progress commit in one transaction.

**The historical interval is bounded, not a rewind ([#151](https://github.com/zanminwang/axton/issues/151)).** Bootstrap could have been a second cursor that delivery rewound to zero and caught up from. It is not: the delivery cursor only moves forward (A2, D9), so a separate `bootstrap_cursor` walks `(B, S]` with `S` fixed at the subscription's origin. That bound is what makes the walk terminate under sustained publication, because a record republished after `S` leaves the interval and becomes the subscription's own delivery; the final page's barrier is what joins the two paths. Compacted positions - one retained invalidation per record per channel - are the mechanism, not a defect: a page of fifty rows can span more than fifty positions.

**Nothing is silent ([#51](https://github.com/zanminwang/axton/issues/51), [#122](https://github.com/zanminwang/axton/issues/122)).** Skipping a change the client cannot use keeps one bad record from blocking a channel, but the application is told. A divergence shows the authoritative base rather than guessing a merge; the queued operation still reaches the server, whose handler decides.

## 11. Risks and Technical Debt

**Accepted limitation.** The subscription epoch and the issued-pull memory live in the process. A page for a pull that was not issued through the client is judged by the cursor gate alone.

**Accepted limitation.** A record whose change was skipped or could not be read stays as it was until it is delivered again (a later publication, or a Mutation or Query whose stored Model output returns it); nothing retries it on its own.

**Accepted limitation.** Stamp/absence evidence is never reclaimed; synchronized release can evict replicated content ([#61](https://github.com/zanminwang/axton/issues/61)). Applying a large page holds one write transaction for its duration; the threading model that keeps that off the host thread is [#134](https://github.com/zanminwang/axton/issues/134).

## Channel evidence and delayed content

[Channel membership](../../../../../crates/client/src/channel_members.rs) folds all evidence before body application. Older evidence is inert and equal contradictory evidence aborts the transaction. A stale positive event needs another current hold before its body can materialize. Last-hold release is eviction rather than stamped null: no cascade, deletion hook or domain mutation. Re-adding can restore an evicted base at an equal stamp; conflicting equal authority remains diagnostic afterward.

Saved Add claims use the same ledger without changing the polling cursor. Request epoch admission guards delayed Load/Fetch/Query/receipt bodies independently of stamps and preserves completion. The coordinated implementation/verification boundary is described in [Common](../../protocol/common.md) and [Reconciliation](../storage/reconciliation.md); prior dated test runs here do not establish the new vertical capability.
