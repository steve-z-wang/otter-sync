# Runtime

## 1. Introduction and Goals

The runtime is the part of the client that owns a task from the moment an SDK submits it to the moment its outcome is delivered: it schedules local work on the one SQLite connection, holds the active application transaction, drives the connection lanes and direct calls, and decides when a result, a status or a change may be observed. Adding a language to AXTON means writing a carrier for JSON strings and adapters for the platform's network, timers and credentials, not a second copy of scheduling, retry, Query completion or Bootstrap rules ([#134](https://github.com/zanminwang/axton/issues/134)).

## 3. Context and Scope

An SDK sees four carrier calls and a wake:

```text
open(request, wake)        -> runtimeId; the open's outcome arrives as a taskCompleted
submit(runtimeId, message) -> admitted, or refused with client_closed when the runtime is gone
drain(runtimeId)           -> the events published so far, in order
detach(runtimeId)          -> no wake runs after this returns; the runtime is forgotten
wake(runtimeId)            -> "drain me"; carries no work
```

Admission is not completion. A submitted task is answered by exactly one `taskCompleted` event; the SDK resolves its Promise, Future or Completer from that event and from nothing else. An envelope that is JSON but not a valid input is admitted and answered with a protocol `report`; a command that does not decode still completes its request with the decoding error, so no waiter is left without an answer. The runtime asks for platform work as *effects* and hears their outcomes as *effect results*; an effect that is no longer wanted is cancelled, and a late result for a cancelled or unknown effect is ignored.

| Direction | Messages |
| --- | --- |
| SDK → runtime | `task {requestId, command}`, `transactionCommand {requestId, transactionId, scope?, companionId?, command}`, `callbackResult {effectId, transactionId, companionId?, ok, error?}`, `effectResult {effectId, outcome}` (a failure's `error` is `{message, status?, retry?}`; `retry: true` is a prerequisite handler's transient failure), `close` |
| runtime → SDK | `taskCompleted {requestId, ok, value, error?, details?}`, `effect {effectId, operation}`, `cancelEffect {effectId}`, `callCompleted {callId, outcome}`, `transactionCallState {callId, state}`, `observerChanged {observerId, snapshot}`, `report {diagnostic}`, `runtimeClosed` |
| effect operations | `callback {transactionId, requestId}`, `mutationLocal {transactionId, companionId, requestId}`, `storeCallback {transactionId, model, changes}`, `http {route, body}` (`push`, `pull`, `action`, `fetch`, `load`), `socket {subscribe}` (a stream: `opened`, `message`, `overflow`, `closed`), `timer {millis}`, `refreshAuth`, `prerequisite {key, name, arguments}` |

Identities: `requestId` is the SDK's increasing counter, never reused; `effectId`, `transactionId`, savepoint `scope`, `companionId` and `observerId` are the runtime's, unique for its lifetime (a `companionId` names one Mutation's local callback and is distinct from a savepoint `scope`); `callId` is the durable call identity of the [protocol](../protocol/actions.md). Every identity travels as a string. The envelopes and the command set are the tagged types in [runtime/protocol.rs](../../../../crates/client/src/runtime/protocol.rs); [fixtures/bridge/envelopes.json](../../../../fixtures/bridge/envelopes.json) is decoded by the Rust, TypeScript and Dart tests alike. A failure the SDK maps to a public error carries a machine-readable `details.code` (`subscription.closed`, `bootstrap.superseded`, `client_closed`, a Bootstrap run's stored code; for a direct call `action.execution_unknown` with the transport failure's `message` and HTTP `status` when there was one, `action.unavailable`, `action.observation_failed`; for a Model Fetch one of the `fetch.*` codes below), so the SDK can keep the cause; other failures are messages. The backend wire protocol is unchanged: the runtime prepares the same bytes the SDKs used to send.

Callers: the [bindings](../sdks/bindings.md), which run one runtime per open client on its own thread. Dependencies: the [frontend interface](frontend-interface.md) for every database operation, the [engine](engine/README.md) for what a receipt, page or response means, and the [connection](connection/README.md) state machines for when to talk to the server.

## 5. Building Block View

`ClientRuntime<S: ClientStore>` in [runtime/mod.rs](../../../../crates/client/src/runtime/mod.rs) is generic over the store and driven by three non-blocking calls: `receive(input, now, entropy)` admits one message and runs no database work; `step(now, entropy)` runs at most one local unit and says whether it did anything; `take_events()` hands over what the steps produced, in order. `now` and `entropy` are facts the caller supplies, so every scenario can be replayed deterministically.

| --- | --- |

| [transactions.rs](../../../../crates/client/src/runtime/transactions.rs) | The one open application transaction: its capability token, savepoint scopes, failure accounting and callback effect |
| [commands.rs](../../../../crates/client/src/runtime/commands.rs) | The local reads, writes, Stream, status and protocol-seam commands executed against the client |
| [effects.rs](../../../../crates/client/src/runtime/effects.rs) | The effect table, cancellation, the continuations effect results become, and the one shared credential refresh |
| [lanes.rs](../../../../crates/client/src/runtime/lanes.rs) | The connection intent and controls, the push lane over `ConnectionDriver` and `SyncCycle`, and the [Downlink worker](connection/controller/downlink-worker.md) driven as runtime work |
| [loads.rs](../../../../crates/client/src/runtime/loads.rs) | Native Load commands, the [Load worker](../../../../crates/client/src/load_worker.rs)'s batches as effects, page application, and the Load handles' observers and waiters ([#173](https://github.com/zanminwang/axton/issues/173)) |

The native side is [bindings/common/src/actor.rs](../../../../bindings/common/src/actor.rs): one thread per client owns the runtime and its SQLite connection, a mailbox admits messages, an outbox publishes events and wakes the carrier. The process-wide registry maps runtime ids to senders and outboxes and is locked only for that lookup ([Bindings](../sdks/bindings.md)).

## 6. Runtime View

**Scheduling.** Ordinary tasks form one FIFO. Inbound work - an effect result, a lane that became due - takes its place in the same arrival order: a lane unit runs when it was ready before the oldest queued task arrived, otherwise that task goes first, and after a lane unit the lane re-enters the order behind everything admitted so far. Neither foreground nor inbound work starves, and the order an application observes is the order things arrived in, as the SDK queues used to provide. One step holds at most one local transaction: a task, a transaction command, a commit or rollback, one Downlink pump (one page, plus the barrier settlement the [Downlink worker](connection/controller/downlink-worker.md#5-building-block-view) documents as its one exception), one receipt settlement, one direct-response application. The runtime never sleeps inside a step: a delay is a `timer` effect the host answers.

**Transactions.** A `transaction` task opens the session, issues a `transactionId` and asks for the application callback as an effect. From then on every ordinary task waits, reads included: none may see or join the open session. The callback's own commands arrive as `transactionCommand`s bearing the id and run on a continuation lane ahead of the parked queue. Nested savepoints keep a stack of runtime-issued `scope` tokens; a command names the innermost open scope or fails as a structural error, and `release` and `rollbackSavepoint` pop only the top. A failed command poisons the unit unless the savepoint it ran in rolls back. The `callbackResult` commits only when nothing is outstanding, no savepoint is open and no failure was recorded; otherwise it rolls back and the parent task fails with the first failure. A command that names a transaction that is not open fails with `transaction_closed`. The SDK keeps the callback's own return value and thrown value in language memory and settles with them once the runtime confirmed the commit or rollback; language-side async-context and zone guards still refuse a captured client from inside the callback, and the runtime's tokens enforce ownership even if a guard were bypassed.

**Mutations and local companions in a transaction.** An application callback may send `submitMutation {name, version, args, store?, local?}` as a transaction command; `local` is a boolean asking for a companion callback, never code or business input (an absent or `null` `local` means none, any other non-boolean is refused). Rust admits it only from an application transaction: an `onStore` capability is refused with `store hook cannot submit a Mutation`, a Query with `cannot be submitted in a transaction`, and Fetch, Load and Bootstrap stay tasks, which no callback can join. Without `local` the command completes with `{callId, ordinal}`. With it, Rust submits the Mutation and its optimism ([Frontend interface](frontend-interface.md#6-runtime-view)), issues a fresh `companionId` and asks for a `mutationLocal` effect naming the initiating `requestId`, which is how the SDK finds the callback. While that capability is active only its own Model reads and writes are admitted, carrying the `companionId`; its writes become companions of that call, never independent direct writes. Any command through the parent capability, one with another or an expired `companionId`, and a Stream, savepoint or submission command through the companion's, is refused with `invalid transaction capability`, a structural failure like a wrong scope, rather than attributed to either owner. The submission answers only at the callback's end: the companion's `callbackResult` restores the parent capability and completes it with `{callId, ordinal}`, or fails it with the callback's error, the first failure of its commands, or `unawaited transaction operation` when companion commands are still queued (those fail `transaction_closed`). It never commits or closes the transaction. A companion failure poisons the enclosing transaction or savepoint under the ordinary rule above, and no usable Call results; a transaction that ends while a local callback runs cancels its effect.

The Call is provisional until the transaction commits. The runtime records provisional call IDs per transaction and savepoint scope and publishes `transactionCallState {callId, state: "committed"}` only after the SQLite commit succeeds, before the transaction task succeeds; a rollback of the transaction or of a savepoint, a failed commit and close publish `rolledBack` for the Calls of the discarded scope only. The push lane cannot see uncommitted queue rows, so no provisional call is sent. Incoming authority, including a Load page, waits behind the open transaction like every other writer, and watches see only the committed result. Durable execution and settlement then follow the ordinary path, whether or not an SDK still holds the Call.

**Incoming authority hooks.** An open client registers optional Model names at open. The runtime validates them against the requested schema, or the pending target schema while an incompatible old replica drains. It suspends these callbacks until that replica rebuilds, then uses the same fixed registration. For a delivery with eligible incoming changes, Rust retains one session through reversible preparation, sequential Model callbacks in schema-name order, authority application and commit ([Frontend interface](frontend-interface.md#6-runtime-view)). The SDK receives one `storeCallback` effect per nonempty registered Model, with an internal transaction capability; it can issue only its own local commands while ordinary tasks wait. The callback has no public request ID. A stale or cancelled effect cannot resume the transaction. Completion, watch and subscription events follow the final commit. The detailed payload and eligibility rule belongs to [Pull](engine/pull.md#6-runtime-view).

A callback failure reports `store_hook_failed` with Model and path; a same-process SDK may attach the original thrown cause. The effect ID only correlates that cause inside the bridge. Close cancels the effect and rolls back without waiting for unresolved application code. If physical rollback fails, the runtime reports it once and closes before admitting another write. A successful logical auto-rollback is not a cleanup failure. A pending callback holds this client's writer, as an ordinary application transaction does; another client remains independent.

**Network work holds no writer.** A direct call prepares its exact request, parks on an `http` effect and a deadline `timer`, and applies the response in a later unit; success is answered only after that commit, with the response's own outcome. A 401 asks for one `refreshAuth` effect, shared with the lanes, then re-sends the same body once under the same deadline. Stopping the connection fails a call still waiting on the network with `action.unavailable`, but a response already in hand is applied and answers its outcome; closing the client fails every call. Query once is decided here too: a saved result completes at once, a request for the same key is joined, otherwise one is fetched and every joined caller completes with its outcome. The push lane freezes a batch in one unit, sends it as an effect, and settles the receipt in another; `callCompleted` for a durable call follows the settlement commit. The Downlink worker's actions become effects - `open` a socket, `request` a pull, `wait` a timer - and its events come back from their results, handed to the worker the moment they are admitted (its enqueue path touches no database), so its 64-frame page queue and overflow recovery bound what a busy socket can pile up while a callback holds the writer; its gap recovery, Bootstrap slot and fairness are unchanged. Every task or continuation that committed wakes both lanes.

**Model Fetch ([#153](https://github.com/zanminwang/axton/issues/153)).** A `fetch {model, version, identity, store?}` task is a direct call on the same lifecycle - frozen body, an `http` effect with route `fetch`, the deadline timer, the one shared refresh that resends the same call ID, response admission, stop and close - under its own codes. Before any I/O the runtime refuses a non-boolean `store` (`null` included), a version other than the local Model read version, an unknown Model or an invalid identity (`fetch.invalid_options`), and any Fetch while an incompatible replica drains (`fetch.schema_pending`), since onStore is suspended then. An identical request in flight is joined: the key is (replica generation, Model, version, canonical identity, store), so omitted and `true` store join, property order does not matter, and different policies do not. The flight stays joinable until its terminal outcome, including while its response waits for the writer (a task submitted while its onStore callback holds the writer waits behind that transaction like any task, and then reads again), and every terminal path removes it and fails or completes every joined caller, so the next call reads again. There is no durable Fetch job and no `callCompleted`. A response is validated against the frozen request, then applied as one single-record delivery ([Frontend interface](frontend-interface.md#6-runtime-view)): through the onStore session when the Model has a hook, in one short write otherwise, and not at all for `store: false` or a backend refusal. Every caller then completes with the invocation's own `{outcome}`, never a reread of the local row; a backend refusal keeps its code (`loader.failed`, the Loader's refusal code, `model_version_unsupported`, `call.identity_conflict`, ...). Local failures are `fetch.unavailable` (no connection, stop before the response, close), `fetch.timeout`, `fetch.transport_failed` (with the transport `message` and `status`), `fetch.invalid_response`, `fetch.store_failed` (a conflict, an unstorable record, a refused onStore callback, which carries `callbackEffectId` for the SDK's cause, or a failed commit), `fetch.schema_pending` and `fetch.schema_changed` (a rebuild replaced the replica). A closed runtime refuses admission with `client_closed`, as for every task.

**Native Loads.** One [Load worker](connection/controller/load-worker.md) per runtime ([load_worker.rs](../../../../crates/client/src/load_worker.rs)) decides which frozen pages go out; the runtime executes its decisions ([#173](https://github.com/zanminwang/axton/issues/173)). A dispatch sends the oldest ready pages, at most 8 and within the 1 MiB request bound, as one `http` effect on the `load` route with a per-attempt deadline `timer` (the connection's `directTimeoutMs`); nothing waits for a batch to fill, at most two batches are out, and a job never has two pages in flight. A batch keeps its slot until every one of its answers was applied, recorded or found stale, so at most sixteen answers wait for the writer. Dispatch and application are lane units that alternate with the Downlink and push lanes, one page per unit; a page is stored through the same owned session, refusal check, `onStore` callbacks and commit as any other delivery, and a failure found while storing is recorded by the next unit. A transport failure, deadline, uncorrelated response or retryable item keeps the frozen call ID and backs off 1 s doubling to 30 s with the lanes' jitter, from the attempt count the ledger persists; a reopen recomputes the delay; retrying a job that backs off keeps its delay. A frozen page that cannot be sent even alone fails its job `load.request_too_large` without holding back the others; such failures share their dispatch step's slot, so they count against the same bound of sixteen waiting answers. A whole-request 4xx other than 401, 408 and 429 sends each page of that request alone next time, and a page refused alone fails its job `load.protocol_invalid`; 408, 429 and 5xx back off. A 401 joins the one shared refresh and resends once; a refresh refused with status 401 or 403 fails the batch's jobs `load.unauthorized`, any other refresh failure backs off. Both SDKs' `refreshAuth` executors pass the status the application's failure carries (TypeScript an error's `status`, Dart an `HttpFailure` or `AuthenticationExpired`). Pause and stop abandon unanswered batches without backoff; answers in hand still apply. Each `loadStart`/`loadGet` handle gets an observer publishing `{kind:"load", status}` after the commit it describes, with a pending job projected as `loading` (page in flight), `waiting` (offline, paused, backing off, pending rebuild) or `pending`; `loadWait` parks on the job's current run and settles only from that run. Close fails waiters `client_closed` and a rebuild fails them `load.schema_changed`, ending the observers; neither cancels a job. A rebuild's terminal snapshot carries a `failed` status with that error, and for the rest of the session status, wait, cancel, retry and forget of a job the rebuild abandoned answer `load.schema_changed`, not `load.not_found`. A page refused for its records emits the same records report as other deliveries before its failure is recorded. A start whose first request exceeds the request bound fails `load.request_too_large` and stores nothing. Load commands are tasks, so a callback transaction or `onStore` cannot issue them. The job ledger, once mappings and page fence are [Loads](engine/loads.md); the pending-rebuild parking and abandonment are [Reconciliation](storage/reconciliation.md#6-runtime-view).

**Prerequisite handlers ([#185](https://github.com/zanminwang/axton/issues/185)).** The open request's `prerequisiteHandlers` names the prerequisites the SDK runs handlers for, validated against the requested schema and fixed for the runtime's lifetime, as `storeHooks` are. The scheduler turns dirty at open, after every committed task or continuation (the commit that wakes the lanes), after a handler's outcome, a `readiness` task, its timer and a rebuild. A dirty scheduler with no handler running takes one lane unit after the ready continuations: it reads the pending tasks and issues one `prerequisite` effect for the first one with a handler that is not backing off. A success or a plain failure is recorded by the next unit; a failure with `retry: true` writes nothing and backs the task off in memory, and one `timer` effect waits for the earliest retry, which the host's timer releases. Connected or not, the scheduler runs. The runner's contract is [Prerequisites](../schema/prerequisites.md#5-building-block-view).

**Unsent work ([#186](https://github.com/zanminwang/axton/issues/186), [#205](https://github.com/zanminwang/axton/issues/205)).** A task `unsentWatch {view}` registers an observer of `rejections` (the retained refusals, each with the act as submitted), `failures` (the unsent calls blocked on a failed task, with those tasks) or `pending` (the number of queued, unsettled calls), answers its `observerId` and publishes `{kind: "rejections" | "failures", items}` or `{kind: "pending", count}` behind the answer. It follows the watch rule below - re-run after every commit, including a prerequisite outcome's, and published only when it differs - and `unwatch` ends it. `rejectionGet {id}` reads one refusal or `null`; `dismiss {ordinal}` removes one; `retryTasks {keys}` makes tasks pending in one local transaction and forgets their backoff, so the handler registered at open runs them; `discard {ordinal}` removes an unsent call without recording a refusal for it and announces the `callCompleted` of it (`dropped`) and of each refused dependent after the commit, like `drop`. The shapes are the engine's ([Frontend interface](frontend-interface.md#6-runtime-view)). Inside an application transaction `dismiss`, `retryTasks` and `discard` are transaction commands: they run in the session, so the callback's later commands see them, and what they announce waits for the commit - the Call completions after the `transactionCallState` of the transaction's own calls and before its answer, and a retried task's backoff reset, after which its handler runs. A savepoint rollback forgets the announcements of its scope; a rollback, a failed commit or close forgets them all. A local callback's capability refuses them as it refuses any non-local command, and an onStore session refuses them in the engine.

**Observation after commit.** Subscription status is projected from the runtime's own connection state and published as `observerChanged` snapshots only when it differs from the last one; Bootstrap waiters settle on the committed transition of the run they registered with; a watch or unsent-work observer re-runs after every commit and publishes only a result that differs, never while a callback transaction is open. A watch whose first query fails is never registered: its task fails. A terminal snapshot (`closed: true`) ends a subscription observer on unsubscribe, rebuild and close, and a watch or unsent-work observer on close; `unwatch` ends either without one.

**Watched SQL** ([#184](https://github.com/zanminwang/axton/issues/184)). `watchSql {sql, parameters}` asks the store which tables the statement reads ([Queries](engine/local-operations/queries.md)); it is refused unless it is one read-only `SELECT` or `WITH … SELECT` reading no `axton_*` table, and a statement SQLite cannot prepare or run fails the task the same way. It then runs on the committed reader and registers a watch observer whose snapshots, `unwatch`, close and rebuild behaviour are a `watch`'s. It does not follow the every-commit rule: the runtime holds the client's `watch(tables)` receiver for the tables it reads, which every commit path signals after its commit - a local write, a settlement or rejection rollback, an optimistic replay, a Stream, Load or Fetch page, a rebuild - and at the end of a unit with no callback transaction open only a signalled statement re-runs. A commit that writes none of its tables costs it nothing. `unwatch` and close remove its engine watcher by id, and a statement that reads no table a commit writes (`SELECT 1`, SQLite's own `sqlite_*` tables) registers none, so mounting and unmounting a view leaves nothing behind.

**Close and rebuild.** `close` is priority control: it rolls back an open session, cancels every effect (a prerequisite handler's too), fails every queued and parked task with `client_closed`, ends every observer, and announces `runtimeClosed` only after the store is released, so the carrier may delete or reopen the files the moment it sees it. Durable accepted work stays in SQLite for reopen. A `rebuild` cancels every lane and direct effect (a direct call in flight fails with `action.execution_unknown`, a Fetch with `fetch.schema_changed`, and the replica generation changes so no later Fetch joins an old flight), resets the worker in place so it keeps its socket epoch and request allocators and the application's running or paused intent ([#162](https://github.com/zanminwang/axton/issues/162)), closes every subscription observer (the identities belong to the file left behind), cancels the prerequisite handler in flight, forgets every prerequisite backoff and scans the new replica, and keeps the watches.

## 9. Architecture Decisions

**Rust owns the task, the host executes effects.** Putting all I/O in Rust would fix the platform boundary the SDKs need (Node's `fetch` and `ws`, Dart's `HttpClient`, the browser Worker of [#59](https://github.com/zanminwang/axton/issues/59)); leaving orchestration in each SDK duplicated every lifecycle rule. The runtime therefore requests effects and decides on their outcomes, and the host runs them.

**One actor per client, no process-wide execution lock.** A single actor would serialize independent clients; a lock held during database work or while waiting for a callback did the same. The registry lock covers map access only.

**No durable response inbox.** An admissible push receipt may be held in memory for local hook/application retry; malformed or inadmissible replies are discarded and the unchanged frozen request is retried over the network. Reopen uses the backend's saved outcome, and rebuild clears the in-memory receipt. Task completions, effect replies and lifecycle control are lossless in memory; foreground memory stays proportional to outstanding callers, as the SDK promise queues were. Accepted user work is durable in SQLite already; a direct call's result was never stored.

**Admission order, not turns.** Alternating foreground and lane turns let an inbound page be applied ahead of an unsubscribe that had been requested before the page arrived. Arrival order is what the application can reason about.

## 11. Risks and Technical Debt

**Accepted limitation: foreground memory is proportional to outstanding callers.** The runtime never evicts an accepted task or a result; an application that submits faster than it drains grows its routes and the outbox, as it grew the SDK promise queues before. No public overload policy was added by [#134](https://github.com/zanminwang/axton/issues/134).

**Accepted limitation: watches re-run after every commit.** The runtime keeps the SDKs' coarse rule for `watch` - any commit, including the push lane's own freeze, re-runs every Model watch and publishes only what changed. Dependency-aware notification is [#16](https://github.com/zanminwang/axton/issues/16). A watched SQL statement already re-runs only for the tables SQLite says it reads.

**Accepted limitation: watched SQL is table-grained.** A commit to a table the statement reads re-runs it even when no row it selects changed; the comparison then publishes nothing. A statement's tables are fixed when it registers: a rebuild re-runs it but does not ask SQLite again.

**Guards without an end-to-end test: a Fetch in flight when a drain starts or a rebuild runs.** A drain is decided only at open, a rebuild runs only during a drain, and Fetch is refused throughout a drain, so no Fetch can be in flight at either moment through the public lifecycle. The discard of such a reply (`fetch.schema_pending` at apply) and the rebuild fence (`fetch.schema_changed`, replica bump) are therefore checked by inspection only; the reachable path - refusal while draining, then a Fetch on the rebuilt replica - is tested ([#153](https://github.com/zanminwang/axton/issues/153)).

**Not verified on a device.** The React Native carrier is exercised with the Node addon and the mobile transaction adapter; the Expo module is parse-checked and its Rust static library builds for the simulator target, but no simulator or device run is part of the repository gate ([platform smoke tests](../../../../integration/platform/README.md)).

**Follow-up.** Browser support ([#59](https://github.com/zanminwang/axton/issues/59)) reuses the runtime state machine behind a `postMessage` carrier.
