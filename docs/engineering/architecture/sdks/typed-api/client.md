# Client

## 1. Introduction and Goals

An application writes `client.mutations.addTodo(...)`, `client.queries.searchTodos(...)` and `client.models.todo.watch(...)` without seeing JSON or cursors. The client typed API consists of a generic runtime class per language and generated classes carrying the application's Model, Mutation and Query names and types.

## 3. Context and Scope

What an application sees:

| Surface | Purpose |
| --- | --- |
| `GeneratedClient.open({path, server?, connection?, onStore?})` | open the local database; optionally register per-Model incoming-authority callbacks; with `server`, connect and keep syncing |
| `client.models.<model>.get / query / watch / <relation>` | reads on the last commit; `watch` re-emits when results change |
| `client.mutations.<name>(args, options?)` | commit a durable Mutation intent and inferred Model optimism locally; return `Call<Output>` |
| `client.mutations.call.<name>(args, options?)` | execute a Mutation directly and return its final output |
| `client.queries.<name>(args, options?)` | execute a Query directly and return its final output |
| `client.queries.enqueue.<name>(args, options?)` | commit a durable Query intent with no optimism; return `Call<Output>` |
| `client.queries.<name>(args, { once, refresh, store })` | reuse, or save on success, the complete result of a direct Query ([#158](https://github.com/zanminwang/axton/issues/158)) |
| `client.queries.invalidate.<name>(args)` | discard the saved `once` results of one argument set, every store policy, in a local transaction |
| `client.fetch.<model>(identity, { store? })` | read one Model remotely through its Loader, stored locally by default; `Promise<Model \| null>` / `Future<Model?>` ([#153](https://github.com/zanminwang/axton/issues/153)) |
| `client.transaction(tx => …)` with `tx.models.<model>.create / update / delete`, `tx.scopes.subscribe / unsubscribe` | local reads, direct writes and Scope intent in one local transaction |
| `tx.mutations.<name>(args, { store?, local? })` | queue a durable Mutation in that local transaction, optionally with local companion writes from `local`; return a `Call<Output>` that is provisional until the transaction commits |
| `client.scopes.subscribe(scope)` | register durable intent to follow a Scope; answers the runtime's `Subscription` handle |
| `subscription.scope`, `.status`, `.watch(listener)`, `.unsubscribe()` | what one registration is, what it is doing, observation of its changes, and its durable removal |
| `subscription.bootstrap()` | prepare this Scope's published history; resolves when the load completes |
| `client.loads.<name>(args, { once?, refresh? })` | commit a durable native Load job locally and answer its `Load` handle; with `once`, reuse the job an earlier once start of the same arguments registered ([#173](https://github.com/zanminwang/axton/issues/173)) |
| `load.id`, `.status`, `.watch(listener)`, `.wait()`, `.cancel()`, `.retry()`, `.forget()`, `.dispose()` | one job's identity, projected status and observation; `wait()` resolves after the final page committed or throws `LoadError` (`LoadException` in Dart) |
| `client.loads.get(id)`, `.list({ limit })`, `.invalidate.<name>(args)` | reattach by ID, the most recent jobs (1..100, default 50), and removal of one argument set's once registrations offline |
| `client.syncState()`, `client.models.<model>.syncState(identity)` | the client's and one record's local sync state |
| `clientId`, `connect()`, `pendingTasks()`, `setReadiness()`, `drop()`, `dismissRejection()`, `querySpec()`, `readSql()`, `watchSql()`, `close()` | identity, connection, recovery and escape hatches, on the same object; `watchSql` observes read-only SQL over several Models |
| `client.rejections.watch / get / dismiss`, `client.failures.watch / retry / drop`, `client.outbound.watchPending`; `tx.rejections.dismiss`, `tx.failures.retry / drop` | unsent work account-wide ([#186](https://github.com/zanminwang/axton/issues/186)): the refusals with the act as submitted (`RefusedAct`, `SubmittedAct`, `ActOperation`), the calls blocked on a failed task (`FailedAct`, `FailedTask`) and the pending count, as streams with the lifecycle of `watch` (TypeScript: a listener and `onError`, returning a stop function; Dart: a `Stream`); the same resolutions in an application transaction commit or roll back with it ([#205](https://github.com/zanminwang/axton/issues/205)) |
| `open({ prerequisites })` (Dart `open(prerequisites:)`), `PrerequisiteRetry` | the prerequisite handlers by prerequisite name, registered once and run by the runtime; a handler throws `PrerequisiteRetry` to be retried with backoff ([Prerequisites](../../schema/prerequisites.md#5-building-block-view)) |

Every call becomes one task of the client's [runtime](../../client/runtime.md), submitted through the SDK Bridge and the [bindings](../bindings.md). Generated code depends on the runtime package (`@axtonjs/client`, `package:axton`); the generic runtime depends on nothing generated.

The concrete generated client exposes standalone `client.models` local CRUD/read/watch, transaction `tx.models` local CRUD/read without watch, transaction `tx.mutations` for queued Mutations only, and the `mutations` and `queries` namespaces. Each method fixes its delivery and return type; the four routes and their await boundaries are owned by [Mutations and Queries](../../schema/actions.md#3-context-and-scope). There is no `client.actions`. The generated methods use the SDK's shared types: TypeScript `Call`, `CallStatus`, `CallOutcome`, `CallError` and `CallOptions`; Dart `Call`, `CallStatus`, `CallOutcome`, `CallSuccess`, `CallFailure`, `CallError` and `CallStore`. Inside an application-owned local transaction the only backend route is the queued Mutation, as `tx.mutations.<name>`; `tx.mutations.call`, Queries, `enqueue`d Queries, Fetch, Load and Bootstrap are absent. Standalone local Model writes use their own local transaction and do not enqueue backend work.

**Mutations in an application transaction.** Three commit boundaries are distinct. The transaction is local and atomic: its reads, direct writes, Scope intent, queued Mutations, their optimism and their companions commit together or not at all. A companion follows its own Mutation's backend outcome: kept on acceptance, removed on terminal rejection, with later local writes kept in place, and never above newer server authority for the same record ([Settlement](../../client/engine/settlement.md#6-runtime-view)). Each Mutation has its own backend outcome, so a transaction is not a distributed transaction: calls in one transaction form no backend group, gain no execution dependency beyond those their Model operations infer, and an accepted call is not undone when a sibling is rejected. Work that must succeed or fail together at the backend belongs in one Mutation.

`tx.mutations.<name>(args, options?)` takes the generated options of the durable route, extended with `local`, a callback that receives a restricted local context: typed Model reads, which see the transaction's earlier writes and this Mutation's optimism, and create, update and delete, which apply at once and are recorded as that Mutation's companions. The context (generated `CompanionContext`, with `models` only) has no Mutation, remote, watch, Scope or savepoint member. A captured outer transaction or client used inside the callback is refused. The context expires when the callback completes: a command through it afterwards is refused with `invalid transaction capability` and poisons the transaction while it is still open, and fails `transaction_closed` once the transaction ended. The callback runs once, in the transaction; its writes are stored as operations, so a reopen, retry or receipt never runs it again. Omitting `local` adds no companion, and `local` is never serialized into args or a request. Only this method takes `local`; standalone, direct and Query methods do not. Dart takes `local` as a named parameter, renamed `callLocal` when a business input is named `local`, as `once` becomes `callOnce`.

The method resolves after the Mutation's optimism and its callback ran in the open transaction, with a `Call<Output>` that is provisional until commit: `status` stays `pending` but proves no durable submission. `wait()` before commit rejects at once with a `CallError` whose `code` is `transaction_uncommitted` (`execution: unknown`, since the call may still run) without cancelling the Mutation, and after commit the same handle observes normal execution. A handle whose transaction or savepoint rolled back becomes `failed` and its `wait()` rejects with `transaction_rolled_back` (`execution: rejected`: it is never sent). Both are local lifecycle errors, not backend rejections or outcomes; an uncaught one fails the transaction callback as any thrown error does. A submission that fails - an invalid argument, a refused Query, a thrown or failed `local` callback - rejects with the runtime's error or the thrown value, not a `CallError`; only invalid options are `CallError` `action.invalid_options`. In TypeScript a failed command the callback caught rejects the submission with that very object; Dart leaves it to the runtime, which fails the submission with its own `StateError`, as Dart's outer transaction does. `client.transaction` still returns its callback's value after commit, so the callback returns one Call, several, or none; the transaction has no Call or backend result of its own. Dropping a Call cancels nothing. Incoming-authority callbacks have no `mutations`. React Native generates the same shape through its transaction adapter, which has no savepoints.

**Incoming authority callbacks.** Optional `onStore` keys use generated Model accessor names. TypeScript exports `StoreHooks`, `StoreHandler<Identity, Model>` and a discriminated `StoreChange<Identity, Model>`; Dart exports `StoreHooks`, `StoreHandler<I, M>` and sealed `StoreUpsert<I, M>`/`StoreDelete<I, M>`. An upsert provides its typed identity and full incoming row, a delete its typed identity. Neither provides previous content or Scope provenance. The generated and raw adapters copy both registration names and callback function values at open. The raw SDK accepts a Model-name-keyed map; the generated adapter decodes with the Model's existing codecs. [Pull](../../client/engine/pull.md#6-runtime-view) owns trigger, grouping and pre-store view rules.

The callback receives an ordinary local transaction. Its `tx.models` operations and `tx.scopes.subscribe/unsubscribe` commit with incoming authority; the Scope methods resolve `void` / `Future<void>`, return no Subscription and await no network. Remote Mutation/Query calls, enqueueing, Bootstrap and captured outer-client work cannot join this transaction. An expired callback handle cannot issue later commands. A thrown callback rejects local application with `store_hook_failed`; diagnostics name the Model and path, and a same-process SDK retains the original cause when available. Direct calls and all joined `once` callers reject after local failure without an automatic backend retry; an older valid once snapshot remains. Durable calls settle only after local commit. A callback may run again on delivery retry and may block its Scope or frozen push batch if it keeps failing. [Runtime](../../client/runtime.md#6-runtime-view) owns cancellation and [Settlement](../../client/engine/settlement.md#6-runtime-view) owns receipt recovery. React Native uses the same generated TypeScript shape but retains its conservative outer-client guard during the callback and has no nested savepoint API.

**The subscription handle.** `subscribe` resolves when its local transaction commits: it awaits no authentication, connection or acknowledgement, so registering a Scope with no network is an ordinary offline write, and repeated calls for the same live registration answer the same cached handle, keyed by persistent subscription identity. `status` is one frozen snapshot with three parts, and `watch` delivers the current snapshot then every change until its returned function is called:

| Part | Values and meaning |
| --- | --- |
| `active` | whether this handle still names a live registration |
| `initialization` | `pending` until a durable starting boundary exists, then `ready`. It is a statement about committed state, not about the socket |
| `connection` | `offline` (no lane, or paused), `connecting` (no session, or one that has not covered this Scope yet), `catching-up` (a delta request is out), `live` (the session delivers normally - not that all history is loaded), `stopped` (the handle is closed) |
| `bootstrap` | `{phase, error}` of this Scope's durable load: `not-requested`, `waiting-for-initialization` (registered, but no starting boundary bounds its interval yet), `loading`, `catching-up` (the interval is loaded and the fixed completion barrier is waiting for ordinary delivery), `complete`, `failed` with the stored `{code, message}` |

**`bootstrap()` ([#151](https://github.com/zanminwang/axton/issues/151)).** `subscription.bootstrap()` prepares the Scope's published history. It submits its `scopeBootstrap` task when the call is made, whether or not the returned Promise/Future is awaited, and it resolves only after the completion transaction commits. Calls during one active run share that run, a call after a valid completion resolves locally - offline too - and a call after a terminal failure explicitly retries the saved run; the calls a failed run belongs to stay failed, because the runtime parks each waiter on the run its registration answered with. A waiter whose run is no longer the newest one observed can no longer see its own outcome, and it never resolves from another run's: it is rejected with `bootstrap.superseded`. Completion means the initial publication coverage was processed under the [reported read-failure contract](../../server/engine/pull.md#9-architecture-decisions): it is neither a transactionally frozen whole-Scope snapshot, nor a promise that every record loaded, nor a statement about current freshness. Waiting for connectivity is not failure and has no implicit timeout. `unsubscribe()` takes that epoch's load state with the row and rejects the waiters of that handle with `subscription.closed`; a call that raced the removal and reached the engine after the row went is rejected with `subscription.closed` too, not with the engine's own refusal text - the runtime completes it with `details.code: "subscription.closed"`, which the SDKs map; closing the client rejects only this process's waiters, with `client_closed`, and preserves the durable task, which a reopened client resumes without a new call. No task-cancel or forced-refresh API exists in this milestone.

**Bootstrap and the subscription cover delivery together, and the barrier is what joins them.** Let *S* be the origin the subscription committed, *B* the load's own progress and *L* the ordinary delivery position. The load walks `(B, S]`; the subscription delivers after *S*. For every identity published before *S*, either its retained position is still in that interval and the load reads it, or its latest publication moved above *S* - a republication, an update - and the subscription delivers it instead. Because *S* never moves, the walk terminates however much is published beside it. The final historical page records the scope head *H* its own transaction saw, and the run completes only at `B = S` and `L >= H`: that fixed barrier is what makes "either the scan or delivery covered it" a statement about a moment rather than a race. Record stamps settle which version wins whichever path arrives first, so a page resolved at older stamps cannot regress newer authority or resurrect a newer deletion, and pending optimistic edits replay over what lands under the existing rules.

**What it is not, and what it assumes.** The coverage is publication-based: the load enumerates the identities published to the Scope and resolves them through the owner's Loaders. It does not infer current membership from business relationships, discover records nobody published, implement move-out rules, delete local content on unsubscribe, or maintain an arbitrary query result. A Loader `null` is authoritative absence; a read error is not absence, and such an error may predate the call - this milestone adds no durable per-record failure queue. Public documentation must therefore distinguish *processed* loading and delivery from *successfully resolved* records, and must not present `await bootstrap()` as a fresh snapshot or as proof that every record loaded. The argument assumes retained invalidation identities, monotonic publication cursors, eventual delivery and successful authoritative reads; retention ([#61](https://github.com/zanminwang/axton/issues/61)), current-membership removal ([#140](https://github.com/zanminwang/axton/issues/140)) and eviction ([#139](https://github.com/zanminwang/axton/issues/139)) must preserve or replace that contract. Coverage is also scoped to the same authenticated principal as the retained store: principal switching and out-of-band SQL are outside it, and a replica rebuild or an incompatible read-contract change resets it through the existing reconciliation path. Diagnostic scales belong to [#12](https://github.com/zanminwang/axton/issues/12); no capacity or latency claim follows from these tests.

**A new subscription delivers from its origin, not from the beginning of the Scope** ([#150](https://github.com/zanminwang/axton/issues/150)): the first head the server acknowledges becomes its starting boundary, so records published before it are not loaded, and `live` says the stream is healthy rather than complete. Loading a Scope's existing records is the explicit `bootstrap()` operation of [#151](https://github.com/zanminwang/axton/issues/151). `unsubscribe()` commits the removal of that identity and stops the handle; repeating it is a no-op, and it cannot remove a later registration of the same Scope name. Other work through a closed handle fails with `subscription.closed` (`SubscriptionClosedException` in Dart). Closing the client stops every handle and cancels its observers, and deletes no subscription. A [rebuild](../../client/storage/reconciliation.md) replaces the replica with fresh registrations, so it stops every handle taken before it the way a removal does - `active` false, `connection` `stopped`, observers completed - and a later `unsubscribe()` through one of them is a harmless no-op. A Scope name that is empty or only whitespace names no Scope and is refused before anything is written, the same rule the socket's subscribe frame is held to. An observer's exception is reported through the host's uncaught-error scope after the commit, never turned into a transport failure or a rollback.

A durable call returns its handle after initial local acceptance and commit; that is not final backend success. The handle exposes only `status` and `wait()`, with `wait()` yielding either a result or a `CallError`. An initial local failure rejects before a handle exists. Only a durable Mutation derives optimism; a queued Query commits an intent with no Model operations. Direct calls skip the queue and automatic optimism, returning the result or rejecting with `CallError`; offline, they fail rather than enqueue. Each direct invocation takes a fresh call ID. A Model result is a per-invocation Loader snapshot: a later call in the same batch may change the batch-final settlement authority, and current local reads may include later optimism. Live handles keep business results in memory while pending/completion state remains durable.

Create inputs admit omission only for fields with a creation default ([Models](../../schema/models.md#9-architecture-decisions)): TypeScript `{Model}Create`, whose encoders leave an omitted field out; Dart `{Model}CreateInput`, satisfied by a complete `{Model}` or by `{Model}Create`, where a defaulted nullable field is `Present<T?>?` so an explicit null is distinct from omission. Local `create`, legacy slot creates and Mutation create operands (single, optional, list) take these types; full records and backend handler arguments stay complete. The SDKs never generate a value: the native client fills omitted fields once, before the write or request, and local `create` still resolves with no value.

All four routes take an optional `store` option beside the args ([protocol](../../protocol/actions.md#store-policy)). TypeScript generates `{Name}Options`, whose `store` is a boolean or a partial map restricted to the operation's explicit Model output names (boolean-only when there are none). Dart generates a `{Name}Store` selector with `all()`, `none()` and, when eligible outputs exist, `outputs(...)` with nullable booleans; the named parameter is `store`, or `outputStore` when a business input is already named `store`. The durable route validates and persists the policy with the call ID, args and optimism in one local transaction; the direct route validates it before dispatch.

## 5. Building Block View

- **Ports.** Read, write and live ports separate capabilities: a write port adds local direct writes to reads; a live port adds `watch`. A transaction implements the write port and cannot watch, invoke a Query or call a Mutation directly; an application transaction also queues Mutations through the raw transaction's `submitMutation(name, version, args, decode, options)` (the generated `SubmitMutationPort`), and a `local` callback gets a separate `LocalTransaction` adapter that implements the write port through the companion capability only. [Generated code](../../compiler/generate.md) binds Model classes to these ports; `makeMutations` and `makeQueries` (TypeScript) and the Dart `Mutations`, `DirectMutations`, `Queries` and `QueuedQueries` classes bind operations to a `CallPort` through its existing `invokeAction` (durable) and `invokeDirectAction` (direct) members.
- **TypeScript hosts.** Node and React Native share the [client](../../../../../packages/client-js/runtime.mts) and its [Bridge](../../../../../packages/client-js/bridge.mts). Each entry point supplies its native carrier, transaction object and server transport. Node retains AsyncLocalStorage savepoints; React Native uses an explicit transaction scope without a nested-savepoint API.
- **Client.** Every method submits one task to the [runtime](../../client/runtime.md) and settles from that task's completion; the runtime orders local work, so the SDK keeps no queue of its own. `transaction` submits a `transaction` task and runs the body when the runtime asks for its callback, against a transaction object bound to the runtime-issued `transactionId`; the body's own return value stays in language memory and is returned only after the runtime confirmed the commit. A durable call is one `submitAction` task: the runtime commits the intent and inferred optimism together, the handle is registered while that task's completion is dispatched, so the `callCompleted` that follows the settlement commit always finds it, even in the same batch. A direct call is one `invoke` task, which the runtime prepares, sends, bounds and applies; its value is `{outcome}` after the apply commits. A Model Fetch is one `fetch` task with the same `{outcome}` value; the SDK neither joins, retries nor caches it. `connect` installs the effect executors ([client-js/connection.mts](../../../../../packages/client-js/connection.mts), [dart/connection.dart](../../../../../packages/dart/lib/src/connection.dart)) and hands the runtime the connection intent.
- **Transaction.** Commands are sent as the callback's transaction commands, in submission order, each carrying the innermost open savepoint's runtime-issued `scope`. `finish` fails if any command was never awaited or if savepoint work overlapped: Promise lifetime and async context are language-side evidence the runtime cannot see. A command that failed although the application caught the error fails the transaction with that very object; the runtime refuses the commit for it as well. `savepoint(body)` nests via async context (TypeScript) or zone values (Dart) so a failure inside it is confined to that scope; the runtime refuses a command for any scope but the innermost open one. A `local` callback is registered by the request ID of its `submitMutation` and run, in the submitter's async context or zone, when the runtime's `mutationLocal` effect names that request; its commands carry the runtime-issued `companionId` and the submission's `scope`, a command it did not await fails the submission, and the callback reference is released on completion, admission failure, cancellation and runtime close. While a submission with `local` is unfinished, the transaction refuses every other command, savepoint and submission itself with `invalid transaction capability` and records it as structural, so the refusal never depends on when the runtime receives it; an expired local handle is refused and poisons the open transaction the same way. Node and React Native share this in [local.mts](../../../../../packages/client-js/local.mts). The SDK keeps each provisional Call in the existing call registry and moves it to committed or rolled back when `transactionCallState` arrives, whether or not anyone waits on it.
- **Captured client guard.** Any call on the outer client from inside its own active transaction callback - a read, a watch, a subscription, a nested transaction, a Mutation or Query - fails with `transaction_active` before it is submitted, since it would otherwise wait behind the transaction that is waiting for it. The guard stays active inside a `local` callback. Node uses async context and Dart a zone token to identify that callback exactly. React Native has no async context, so it keeps the narrower rule: Mutation and Query calls are rejected while a public transaction is active, and other outer-client calls wait behind it. The runtime's capability tokens enforce the transaction's ownership even if a guard were bypassed.
- **Subscription handle.** One handle per persistent subscription identity ([client-js/subscriptions.mts](../../../../../packages/client-js/subscriptions.mts), [dart/subscriptions.dart](../../../../../packages/dart/lib/src/subscriptions.dart)). It claims the observer its `scopeSubscribe` task names while that completion is dispatched, keeps the last status snapshot the runtime published and its listeners, submits `bootstrap()` at once and maps the runtime's `details.code` to the public errors, and closes on the terminal snapshot. It computes no status and decides no waiter.
- **Load handle.** A fresh language object per start or reattach, each with its own observer ([client-js/loads.mts](../../../../../packages/client-js/loads.mts), [dart/loads.dart](../../../../../packages/dart/lib/src/loads.dart)). It claims the observer its `loadStart` or `loadGet` task names while that completion is dispatched, keeps the last status the runtime published and delivers only distinct ones, forwards `wait`/`cancel`/`retry`/`forget` as tasks and maps the runtime's `details.code` to `LoadError`/`LoadException`, and ends on the terminal snapshot of close or rebuild. `dispose()` submits `loadDispose` and drops the observer route, so nothing retains a disposed handle; it cancels nothing. The SDK caches no handle, decides no once reuse and runs no page loop.
- **Watch.** Submits a `watch` task and delivers the rows the runtime publishes: the current rows, then every result that differs after a commit. A watch whose first query fails ends at once with that error; a later re-run failure reaches the connection's `onError` and the watch stays. Stopping it submits `unwatch`. Dart exposes a broadcast stream. `watchSql` ([#184](https://github.com/zanminwang/axton/issues/184)) is the same observer over read-only SQL: TypeScript `watchSql(sql, parameters = [], listener, onError?)` returns the stop function, Dart `watchSql(sql, {parameters})` a stream; each submits a `watchSql` task and delivers through the path `watch` uses. The runtime decides which commits re-run it ([Runtime](../../client/runtime.md#6-runtime-view)); the generated `GeneratedClient` forwards it beside `readSql`.
- **Generated code.** Types, codecs (dates to `Date`/`DateTime`; generated Dart encodes every `DateTime` through `AxtonDateTime.toAxtonPrecision()` in [date_time.dart](../../../../../packages/dart/lib/src/date_time.dart), UTC with the sub-millisecond part dropped, so it sends what the core stores), operation input/output bindings, Model classes and the facades `GeneratedClient`, `GeneratedTransaction` and, in a schema with a current Mutation, `ApplicationTransaction` and `CompanionContext` ([Compiler / Generate](../../compiler/generate.md)). The client owns Mutations, Queries and watch; the application transaction (`ApplicationTransaction`, which extends `GeneratedTransaction`; `GeneratedTransaction` itself without a current Mutation) owns local Model reads and writes, Scope intent and the queued `mutations`; the `local` context (`CompanionContext`) owns Model reads and writes only; the `onStore` transaction (`GeneratedTransaction`) keeps local Models and Scopes without Mutations. The three share Model codecs and accessors but not one transaction type. Presence is expressed as an omitted key versus `null` in TypeScript and as `Present<T>?` in Dart; both encode to the same wire patch. An optional Model operand has no such distinction: omitted and `null` are the same argument, recorded and delivered as `null`.

Code: [React Native adapter](../../../../../packages/client-react-native/index.ts), [shared client](../../../../../packages/client-js/runtime.mts), [client-js/bridge.mts](../../../../../packages/client-js/bridge.mts), [client-js/index.mts](../../../../../packages/client-js/index.mts), [client-js/transaction.mts](../../../../../packages/client-js/transaction.mts), [dart/client.dart](../../../../../packages/dart/lib/src/client.dart), [dart/bridge.dart](../../../../../packages/dart/lib/src/bridge.dart), [dart/port.dart](../../../../../packages/dart/lib/src/port.dart).

## 9. Architecture Decisions

**One client object ([#133](https://github.com/zanminwang/axton/issues/133)).** The generated client is the application surface. It exposes `models`, `mutations`, `queries`, `scopes` and `scopes` and carries runtime members directly; the runtime `Client` is an internal handle (`client.client`) used by framework tests. Operation-only and Model-only schemas do not emit an empty obsolete `mutate` facade. The per-record sync state lives beside `get` and `query` on each Model and is typed by its identity.

**Query once snapshots ([#158](https://github.com/zanminwang/axton/issues/158)).** `once` and `refresh` are invocation controls of the direct Query method only; no schema annotation selects them. Generated direct Query methods call the runtime's `invokeQuery` (TypeScript options `{Name}Options & OnceOptions`, in which `refresh` requires `once: true`; Dart named `once`/`refresh`, renamed `callOnce`/`callRefresh` when business inputs take those names), and `queries.invalidate` holds one typed invalidator per current Query (`invalidateQuery`, business args only; a Query may not be named `invalidate`). Mutation and `enqueue` methods keep store-only options; the TypeScript runtime also rejects once controls on them with `action.invalid_options`, while Dart's generic `invokeAction`/`invokeDirectAction` have no such parameters. Likewise only `tx.mutations` takes `local`: the TypeScript runtime refuses a `local` option on `invokeAction`, `invokeDirectAction` and `invokeQuery` with `action.invalid_options` before any work, rather than queue the call without its callback, and the Dart routes have no such parameter. A `once` call is one `invoke {once, refresh}` task, and the Rust [runtime](../../client/runtime.md) decides and executes it: a saved result (`Cached`) completes at once, an active request of the same key and generation (`Join`) attaches the caller to that flight, and a new direct request (`Fetch`) is sent as an `http` effect; the runtime finishes or fails the flight on every terminal path and completes every joined caller with the outcome. The SDK only decodes: each caller parses its own copy. The cached lookup precedes the connection check, so a hit needs no connection. Keys, generations, fencing and the atomic save are the runtime's ([frontend interface](../../client/frontend-interface.md)).

**Model Fetch ([#153](https://github.com/zanminwang/axton/issues/153)).** For a schema with Models the generator emits one Fetch method per Model and a `fetch` member on the generated client, and nothing for a schema without Models. TypeScript emits a `FetchModels` interface, a `FetchPort` contract and `fetchModels(port)`, whose members call `port.fetchModel('Todo', version, encodeTodoIdentity(identity), decodeTodo, options)` with the Model's current local version; the options type is the inline `{store?: boolean}`. Dart emits a `FetchModels` class whose methods take the generated identity class and a named `bool store = true`. `GeneratedTransaction`, the onStore transaction and the raw `Transaction` have no Fetch. The runtime method `fetchModel(model, version, identity, decode, options)` submits `{kind: "fetch", model, version, identity, store?}` and decodes the outcome with the shared direct-call decoder, so each caller builds its own object and a malformed outcome surfaces as `action.observation_failed`. Rust validates `store` and identities; the TypeScript runtime also refuses any option member other than `store` (such as `once`), which Rust would ignore, with `fetch.invalid_options`, and Dart has only the `store` parameter. A backend refusal becomes `CallError(code, "rejected")` as for a direct call; a `fetch.*` task failure becomes `CallError(code, execution, cause)`, with `execution` `rejected` for `fetch.invalid_options` and `fetch.schema_pending` and `unknown` otherwise, and `cause` the refusing onStore callback's thrown value or the transport failure with its status (`HttpFailure` in Dart); `transaction_active` becomes a `CallError`. A closed client's admission error is rethrown unchanged (`Error("client_closed")`, Dart `StateError('client_closed')`), unlike a direct call's `action.unavailable`; a close while the Fetch waits is Rust's `fetch.unavailable`. Transports route `fetch` to `POST /sync/fetch` ([Transport](../../client/connection/transport.md)). The reserved generated names `FetchModels` and `FetchPort` apply only beside Models ([Validate](../../compiler/validate.md)).

**The Scope facade ([#150](https://github.com/zanminwang/axton/issues/150)).** `client.scopes.subscribe(scope)` is the current spelling and the generated `Scopes` class is a thin delegate: it forwards to the runtime's `subscribeScope`, which owns the handle, its immutable status and its observers ([client-js/subscriptions.mts](../../../../../packages/client-js/subscriptions.mts), [dart/subscriptions.dart](../../../../../packages/dart/lib/src/subscriptions.dart)). The generated module re-exports `Subscription`, `SubscriptionStatus`, `BootstrapStatus` and `BootstrapPhase` (with `BootstrapError`, `BootstrapFailedException` and `ClientClosedException` in Dart) so application code can name what it gets back; `bootstrap()` lives on the runtime handle, so the facade grows no member for it. The retained `scopes` facade registers the same Scopes through the same ledger during this milestone, with no second cursor-zero path behind the old spelling; a get-only accessor is deliberately omitted from this first API, and [#152](https://github.com/zanminwang/axton/issues/152) owns removing the old names.

**Native Load facade ([#173](https://github.com/zanminwang/axton/issues/173)).** `client.loads` exists only in a schema that declares a Load, so other schemas keep their generated bytes. It holds one start method per current Load, `get`, `list` and `invalidate.<name>`; the generated methods forward to the runtime's `startLoad`, `getLoad`, `listLoads` and `invalidateLoad` ([Compiler / Generate](../../compiler/generate.md)). TypeScript takes `LoadOptions {once?, refresh?}` as a second argument apart from the business args and types the handle as `Load<'Name'>`; Dart takes named `once`/`refresh`, renamed `callOnce`/`callRefresh` by the Query collision rule when business inputs take those names. The runtime refuses non-Boolean flags and `refresh` without `once` with `load.invalid_options` before any job exists; the TypeScript SDK also refuses an options value that is not an object or names another option. The generated modules re-export `Load`, `LoadStatus`, `LoadPhase` and `LoadError` (TypeScript, with `LoadOptions`) or `LoadException` (Dart); `LoadStatus.name` is the schema operation name and `LoadPhase` is a string union or a Dart enum. Error codes stay open strings: the runtime owns them. `LoadStatus` is `{id, name, version, phase, pages, error}`: `pages` counts committed pages, empty ones included, and `error` is the stored `{code, message}` of a failed or cancelled job (a `LoadException` in Dart). `get` and `list` answer `Load` and `LoadStatus` with `name: string`, since a stored job may name a Load the current schema no longer declares. A TypeScript Load without inputs still takes `{}` (`client.loads.recentTodos({})`); a Dart one takes no argument. A Load has no aggregate result, cursor, delivery override or `store` option: its Models are read through `client.models`.

**Transactional Mutation enqueue and local companions.** The application transaction queues Mutations and executes no remote work, keeping the runtime's rule that network work holds no writer ([Runtime](../../client/runtime.md#6-runtime-view)). Companions are declared per Mutation through `local` rather than inferred from the transaction, so ownership stays unambiguous when one transaction submits several Mutations beside independent writes. The callback runs inside the current transaction instead of opening a nested one. `onStore` stays local-only. There is no standalone companion callback: an application that needs one uses `client.transaction`. Neither the schema syntax nor any backend operation version changes, because `local` is client-only.

**Automatic model-version declaration ([#91](https://github.com/zanminwang/axton/issues/91)).** Generated client configuration identifies the [model versions](../../schema/models.md#9-architecture-decisions) expected by its generated types: the schema embedded in `generated.ts` and `generated.dart` carries each model's `version`, and `open` passes it to the Rust runtime unchanged. The runtime declares those read contracts to the server as `models` on every pull and on the subscribe frame ([Protocol / Pull](../../protocol/pull.md)); application code does not supply versions on each `scopes.subscribe(...)` call. HTTP catch-up and WebSocket delivery must use the same selected contracts. This adds no protocol policy to the SDK: generated metadata passes through bindings to the runtime. Wire placement and validation remain to be designed; read-error behavior follows [failure isolation](../../server/engine/pull.md#9-architecture-decisions).

## 11. Risks and Technical Debt

**Accepted limitation: `refresh` without `once` compiles in TypeScript.** `LoadOptions` is `{once?: boolean; refresh?: boolean}`, so `{refresh: true}` alone type-checks and is refused at runtime with `load.invalid_options` before any job exists. The Query `once` options make that combination a compile error; Loads keep the plain shape the specification defines.

**Accepted limitation: a handle is reachable until `dispose()` or close.** Its observer route must keep it reachable to deliver snapshots, so an application that drops a handle without disposing it keeps that handle alive until the client closes; close ends every observer with a terminal snapshot. A disposed handle is collected.

**Accepted limitation (planned change).** `watch` re-runs its query on every commit, whatever table changed (`watchSql` re-runs only for the tables it reads): the rule now belongs to the [runtime](../../client/runtime.md#11-risks-and-technical-debt), which keeps it for every language. Scoped notifications are [#16](https://github.com/zanminwang/axton/issues/16).

**Accepted limitation.** `Client.open` and the generated `open` still accept a `migration` option that the runtime ignores; its future is part of [#20](https://github.com/zanminwang/axton/issues/20).

**To confirm.** No test runs one script through the Rust, TypeScript and Dart clients and compares state. Both SDKs now drive the same Rust runtime, and the shared envelope fixtures check that their Bridges read and write the same messages, but each still has its own typed API, effect executors and transport, so sharing the runtime alone does not establish equivalent behavior across SDK boundaries. The shared scenarios in `fixtures/scenarios` are prose READMEs, not an executable cross-language runner.
