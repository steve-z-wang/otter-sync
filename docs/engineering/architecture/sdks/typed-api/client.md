# Client

## 1. Introduction and Goals

An application writes `client.mutations.addTodo(...)`, `client.queries.searchTodos(...)` and `client.models.todo.watch(...)` without seeing JSON or cursors. The client typed API consists of a generic runtime class per language and generated classes carrying the application's Model, Mutation and Query names and types.

## 3. Context and Scope

What an application sees:

| Surface | Purpose |
| --- | --- |
| `GeneratedClient.open({path, server?, connection?})` | open the local database; with `server`, connect and keep syncing |
| `client.models.<model>.get / query / watch / <relation>` | reads on the last commit; `watch` re-emits when results change |
| `client.mutations.<name>(args, options?)` | commit a durable Mutation intent and inferred Model optimism locally; return `Call<Output>` |
| `client.mutations.call.<name>(args, options?)` | execute a Mutation directly and return its final output |
| `client.queries.<name>(args, options?)` | execute a Query directly and return its final output |
| `client.queries.enqueue.<name>(args, options?)` | commit a durable Query intent with no optimism; return `Call<Output>` |
| `client.queries.<name>(args, { once, refresh, store })` | reuse, or save on success, the complete result of a direct Query ([#158](https://github.com/zanminwang/axton/issues/158)) |
| `client.queries.invalidate.<name>(args)` | discard the saved `once` results of one argument set, every store policy, in a local transaction |
| `client.transaction(tx => …)` with `tx.models.<model>.create / update / delete` | local reads and direct writes in one local transaction |
| `client.scopes.subscribe(scope)` | register durable intent to follow a Scope; answers the runtime's `Subscription` handle |
| `subscription.scope`, `.status`, `.watch(listener)`, `.unsubscribe()` | what one registration is, what it is doing, observation of its changes, and its durable removal |
| `subscription.bootstrap()` | prepare this Scope's published history; resolves when the load completes |
| `client.channels.subscribe / unsubscribe` | the retained spelling of the same registrations |
| `client.syncState()`, `client.models.<model>.syncState(identity)` | the client's and one record's local sync state |
| `clientId`, `connect()`, `pendingTasks()`, `setReadiness()`, `runPrerequisites()`, `drop()`, `dismissRejection()`, `querySpec()`, `readSql()`, `close()` | identity, connection, recovery and escape hatches, on the same object |

Every call becomes one task of the client's [runtime](../../client/runtime.md), submitted through the SDK Bridge and the [bindings](../bindings.md). Generated code depends on the runtime package (`@axton/client`, `package:axton`); the generic runtime depends on nothing generated.

The concrete generated client exposes standalone `client.models` local CRUD/read/watch, transaction `tx.models` local CRUD/read without watch or backend calls, and the `mutations` and `queries` namespaces. Each method fixes its delivery and return type; the four routes and their await boundaries are owned by [Mutations and Queries](../../schema/actions.md#3-context-and-scope). There is no `client.actions`. The generated methods use the SDK's shared types: TypeScript `Call`, `CallStatus`, `CallOutcome`, `CallError` and `CallOptions`; Dart `Call`, `CallStatus`, `CallOutcome`, `CallSuccess`, `CallFailure`, `CallError` and `CallStore`. No `mutations` or `queries` route may run inside an application-owned local transaction. Standalone local Model writes use their own local transaction and do not enqueue backend work.

**The subscription handle.** `subscribe` resolves when its local transaction commits: it awaits no authentication, connection or acknowledgement, so registering a Scope with no network is an ordinary offline write, and repeated calls for the same live registration answer the same cached handle, keyed by persistent subscription identity. `status` is one frozen snapshot with three parts, and `watch` delivers the current snapshot then every change until its returned function is called:

| Part | Values and meaning |
| --- | --- |
| `active` | whether this handle still names a live registration |
| `initialization` | `pending` until a durable starting boundary exists, then `ready`. It is a statement about committed state, not about the socket |
| `connection` | `offline` (no lane, or paused), `connecting` (no session, or one that has not covered this Scope yet), `catching-up` (a delta request is out), `live` (the session delivers normally - not that all history is loaded), `stopped` (the handle is closed) |
| `bootstrap` | `{phase, error}` of this Scope's durable load: `not-requested`, `waiting-for-initialization` (registered, but no starting boundary bounds its interval yet), `loading`, `catching-up` (the interval is loaded and the fixed completion barrier is waiting for ordinary delivery), `complete`, `failed` with the stored `{code, message}` |

**`bootstrap()` ([#151](https://github.com/zanminwang/axton/issues/151)).** `subscription.bootstrap()` prepares the Scope's published history. It submits its `scopeBootstrap` task when the call is made, whether or not the returned Promise/Future is awaited, and it resolves only after the completion transaction commits. Calls during one active run share that run, a call after a valid completion resolves locally - offline too - and a call after a terminal failure explicitly retries the saved run; the calls a failed run belongs to stay failed, because the runtime parks each waiter on the run its registration answered with. A waiter whose run is no longer the newest one observed can no longer see its own outcome, and it never resolves from another run's: it is rejected with `bootstrap.superseded`. Completion means the initial publication coverage was processed under the [reported read-failure contract](../../server/engine/pull.md#9-architecture-decisions): it is neither a transactionally frozen whole-Scope snapshot, nor a promise that every record loaded, nor a statement about current freshness. Waiting for connectivity is not failure and has no implicit timeout. `unsubscribe()` takes that epoch's load state with the row and rejects the waiters of that handle with `subscription.closed`; a call that raced the removal and reached the engine after the row went is rejected with `subscription.closed` too, not with the engine's own refusal text - the runtime completes it with `details.code: "subscription.closed"`, which the SDKs map; closing the client rejects only this process's waiters, with `client_closed`, and preserves the durable task, which a reopened client resumes without a new call. No task-cancel or forced-refresh API exists in this milestone.

**Bootstrap and the subscription cover delivery together, and the barrier is what joins them.** Let *S* be the origin the subscription committed, *B* the load's own progress and *L* the ordinary delivery position. The load walks `(B, S]`; the subscription delivers after *S*. For every identity published before *S*, either its retained position is still in that interval and the load reads it, or its latest publication moved above *S* - a republication, an update - and the subscription delivers it instead. Because *S* never moves, the walk terminates however much is published beside it. The final historical page records the channel head *H* its own transaction saw, and the run completes only at `B = S` and `L >= H`: that fixed barrier is what makes "either the scan or delivery covered it" a statement about a moment rather than a race. Record stamps settle which version wins whichever path arrives first, so a page resolved at older stamps cannot regress newer authority or resurrect a newer deletion, and pending optimistic edits replay over what lands under the existing rules.

**What it is not, and what it assumes.** The coverage is publication-based: the load enumerates the identities published to the Scope and resolves them through the owner's Loaders. It does not infer current membership from business relationships, discover records nobody published, implement move-out rules, delete local content on unsubscribe, or maintain an arbitrary query result. A Loader `null` is authoritative absence; a read error is not absence, and such an error may predate the call - this milestone adds no durable per-record failure queue. Public documentation must therefore distinguish *processed* loading and delivery from *successfully resolved* records, and must not present `await bootstrap()` as a fresh snapshot or as proof that every record loaded. The argument assumes retained invalidation identities, monotonic publication cursors, eventual delivery and successful authoritative reads; retention ([#61](https://github.com/zanminwang/axton/issues/61)), current-membership removal ([#140](https://github.com/zanminwang/axton/issues/140)) and eviction ([#139](https://github.com/zanminwang/axton/issues/139)) must preserve or replace that contract. Coverage is also scoped to the same authenticated principal as the retained store: principal switching and out-of-band SQL are outside it, and a replica rebuild or an incompatible read-contract change resets it through the existing reconciliation path. Diagnostic scales belong to [#12](https://github.com/zanminwang/axton/issues/12); no capacity or latency claim follows from these tests.

**A new subscription delivers from its origin, not from the beginning of the Scope** ([#150](https://github.com/zanminwang/axton/issues/150)): the first head the server acknowledges becomes its starting boundary, so records published before it are not loaded, and `live` says the stream is healthy rather than complete. Loading a Scope's existing records is the explicit `bootstrap()` operation of [#151](https://github.com/zanminwang/axton/issues/151). `unsubscribe()` commits the removal of that identity and stops the handle; repeating it is a no-op, and it cannot remove a later registration of the same Scope name. Other work through a closed handle fails with `subscription.closed` (`SubscriptionClosedException` in Dart). Closing the client stops every handle and cancels its observers, and deletes no subscription. A [rebuild](../../client/storage/reconciliation.md) replaces the replica with fresh registrations, so it stops every handle taken before it the way a removal does - `active` false, `connection` `stopped`, observers completed - and a later `unsubscribe()` through one of them is a harmless no-op. A Scope name that is empty or only whitespace names no Scope and is refused before anything is written, the same rule the socket's subscribe frame is held to. An observer's exception is reported through the host's uncaught-error channel after the commit, never turned into a transport failure or a rollback.

A durable call returns its handle after initial local acceptance and commit; that is not final backend success. The handle exposes only `status` and `wait()`, with `wait()` yielding either a result or a `CallError`. An initial local failure rejects before a handle exists. Only a durable Mutation derives optimism; a queued Query commits an intent with no Model operations. Direct calls skip the queue and automatic optimism, returning the result or rejecting with `CallError`; offline, they fail rather than enqueue. Each direct invocation takes a fresh call ID. A Model result is a per-invocation Loader snapshot: a later call in the same batch may change the batch-final settlement authority, and current local reads may include later optimism. Live handles keep business results in memory while pending/completion state remains durable.

Create inputs admit omission only for fields with a creation default ([Models](../../schema/models.md#9-architecture-decisions)): TypeScript `{Model}Create`, whose encoders leave an omitted field out; Dart `{Model}CreateInput`, satisfied by a complete `{Model}` or by `{Model}Create`, where a defaulted nullable field is `Present<T?>?` so an explicit null is distinct from omission. Local `create`, legacy slot creates and Mutation create operands (single, optional, list) take these types; full records and backend handler arguments stay complete. The SDKs never generate a value: the native client fills omitted fields once, before the write or request, and local `create` still resolves with no value.

All four routes take an optional `store` option beside the args ([protocol](../../protocol/actions.md#store-policy)). TypeScript generates `{Name}Options`, whose `store` is a boolean or a partial map restricted to the operation's explicit Model output names (boolean-only when there are none). Dart generates a `{Name}Store` selector with `all()`, `none()` and, when eligible outputs exist, `outputs(...)` with nullable booleans; the named parameter is `store`, or `outputStore` when a business input is already named `store`. The durable route validates and persists the policy with the call ID, args and optimism in one local transaction; the direct route validates it before dispatch.

## 5. Building Block View

- **Ports.** Read, write and live ports separate capabilities: a write port adds local direct writes to reads; a live port adds `watch`. A transaction implements the write port and cannot watch or invoke a Mutation or Query. [Generated code](../../compiler/generate.md) binds Model classes to these ports; `makeMutations` and `makeQueries` (TypeScript) and the Dart `Mutations`, `DirectMutations`, `Queries` and `QueuedQueries` classes bind operations to a `CallPort` through its existing `invokeAction` (durable) and `invokeDirectAction` (direct) members.
- **TypeScript hosts.** Node and React Native share the [client](../../../../../packages/client-js/runtime.mts) and its [Bridge](../../../../../packages/client-js/bridge.mts). Each entry point supplies its native carrier, transaction object and server transport. Node retains AsyncLocalStorage savepoints; React Native uses an explicit transaction scope without a nested-savepoint API.
- **Client.** Every method submits one task to the [runtime](../../client/runtime.md) and settles from that task's completion; the runtime orders local work, so the SDK keeps no queue of its own. `transaction` submits a `transaction` task and runs the body when the runtime asks for its callback, against a transaction object bound to the runtime-issued `transactionId`; the body's own return value stays in language memory and is returned only after the runtime confirmed the commit. A durable call is one `submitAction` task: the runtime commits the intent and inferred optimism together, the handle is registered while that task's completion is dispatched, so the `callCompleted` that follows the settlement commit always finds it, even in the same batch. A direct call is one `invoke` task, which the runtime prepares, sends, bounds and applies; its value is `{outcome}` after the apply commits. `connect` installs the effect executors ([client-js/connection.mts](../../../../../packages/client-js/connection.mts), [dart/connection.dart](../../../../../packages/dart/lib/src/connection.dart)) and hands the runtime the connection intent.
- **Transaction.** Commands are sent as the callback's transaction commands, in submission order, each carrying the innermost open savepoint's runtime-issued `scope`. `finish` fails if any command was never awaited or if savepoint work overlapped: Promise lifetime and async context are language-side evidence the runtime cannot see. A command that failed although the application caught the error fails the transaction with that very object; the runtime refuses the commit for it as well. `savepoint(body)` nests via async context (TypeScript) or zone values (Dart) so a failure inside it is confined to that scope; the runtime refuses a command for any scope but the innermost open one.
- **Captured client guard.** Any call on the outer client from inside its own active transaction callback - a read, a watch, a subscription, a nested transaction, a Mutation or Query - fails with `transaction_active` before it is submitted, since it would otherwise wait behind the transaction that is waiting for it. Node uses async context and Dart a zone token to identify that callback exactly. React Native has no async context, so it keeps the narrower rule: Mutation and Query calls are rejected while a public transaction is active, and other outer-client calls wait behind it. The runtime's capability tokens enforce the transaction's ownership even if a guard were bypassed.
- **Subscription handle.** One handle per persistent subscription identity ([client-js/subscriptions.mts](../../../../../packages/client-js/subscriptions.mts), [dart/subscriptions.dart](../../../../../packages/dart/lib/src/subscriptions.dart)). It claims the observer its `scopeSubscribe` task names while that completion is dispatched, keeps the last status snapshot the runtime published and its listeners, submits `bootstrap()` at once and maps the runtime's `details.code` to the public errors, and closes on the terminal snapshot. It computes no status and decides no waiter.
- **Watch.** Submits a `watch` task and delivers the rows the runtime publishes: the current rows, then every result that differs after a commit. A watch whose first query fails ends at once with that error; a later re-run failure reaches the connection's `onError` and the watch stays. Stopping it submits `unwatch`. Dart exposes a broadcast stream.
- **Generated code.** Types, codecs (dates to `Date`/`DateTime`), operation input/output bindings, Model classes and the two facades `GeneratedClient` and `GeneratedTransaction` ([Compiler / Generate](../../compiler/generate.md)). The client owns Mutations, Queries and watch; the transaction owns local Model reads and writes. Presence is expressed as an omitted key versus `null` in TypeScript and as `Present<T>?` in Dart; both encode to the same wire patch.

Code: [React Native adapter](../../../../../packages/client-react-native/index.ts), [shared client](../../../../../packages/client-js/runtime.mts), [client-js/bridge.mts](../../../../../packages/client-js/bridge.mts), [client-js/index.mts](../../../../../packages/client-js/index.mts), [client-js/transaction.mts](../../../../../packages/client-js/transaction.mts), [dart/client.dart](../../../../../packages/dart/lib/src/client.dart), [dart/bridge.dart](../../../../../packages/dart/lib/src/bridge.dart), [dart/port.dart](../../../../../packages/dart/lib/src/port.dart).

## 9. Architecture Decisions

**One client object ([#133](https://github.com/zanminwang/axton/issues/133)).** The generated client is the application surface. It exposes `models`, `mutations`, `queries`, `scopes` and `channels` and carries runtime members directly; the runtime `Client` is an internal handle (`client.client`) used by framework tests. Operation-only and Model-only schemas do not emit an empty obsolete `mutate` facade. The per-record sync state lives beside `get` and `query` on each Model and is typed by its identity.

**Query once snapshots ([#158](https://github.com/zanminwang/axton/issues/158)).** `once` and `refresh` are invocation controls of the direct Query method only; no schema annotation selects them. Generated direct Query methods call the runtime's `invokeQuery` (TypeScript options `{Name}Options & OnceOptions`, in which `refresh` requires `once: true`; Dart named `once`/`refresh`, renamed `callOnce`/`callRefresh` when business inputs take those names), and `queries.invalidate` holds one typed invalidator per current Query (`invalidateQuery`, business args only; a Query may not be named `invalidate`). Mutation and `enqueue` methods keep store-only options; the TypeScript runtime also rejects once controls on them with `action.invalid_options`, while Dart's generic `invokeAction`/`invokeDirectAction` have no such parameters. A `once` call is one `invoke {once, refresh}` task, and the Rust [runtime](../../client/runtime.md) decides and executes it: a saved result (`Cached`) completes at once, an active request of the same key and generation (`Join`) attaches the caller to that flight, and a new direct request (`Fetch`) is sent as an `http` effect; the runtime finishes or fails the flight on every terminal path and completes every joined caller with the outcome. The SDK only decodes: each caller parses its own copy. The cached lookup precedes the connection check, so a hit needs no connection. Keys, generations, fencing and the atomic save are the runtime's ([frontend interface](../../client/frontend-interface.md)).

**The Scope facade ([#150](https://github.com/zanminwang/axton/issues/150)).** `client.scopes.subscribe(scope)` is the current spelling and the generated `Scopes` class is a thin delegate: it forwards to the runtime's `subscribeScope`, which owns the handle, its immutable status and its observers ([client-js/subscriptions.mts](../../../../../packages/client-js/subscriptions.mts), [dart/subscriptions.dart](../../../../../packages/dart/lib/src/subscriptions.dart)). The generated module re-exports `Subscription`, `SubscriptionStatus`, `BootstrapStatus` and `BootstrapPhase` (with `BootstrapError`, `BootstrapFailedException` and `ClientClosedException` in Dart) so application code can name what it gets back; `bootstrap()` lives on the runtime handle, so the facade grows no member for it. The retained `channels` facade registers the same Scopes through the same ledger during this milestone, with no second cursor-zero path behind the old spelling; a get-only accessor is deliberately omitted from this first API, and [#152](https://github.com/zanminwang/axton/issues/152) owns removing the old names.

**Automatic model-version declaration ([#91](https://github.com/zanminwang/axton/issues/91)).** Generated client configuration identifies the [model versions](../../schema/models.md#9-architecture-decisions) expected by its generated types: the schema embedded in `generated.ts` and `generated.dart` carries each model's `version`, and `open` passes it to the Rust runtime unchanged. The runtime declares those read contracts to the server as `models` on every pull and on the subscribe frame ([Protocol / Pull](../../protocol/pull.md)); application code does not supply versions on each `channels.subscribe(...)` call. HTTP catch-up and WebSocket delivery must use the same selected contracts. This adds no protocol policy to the SDK: generated metadata passes through bindings to the runtime. Wire placement and validation remain to be designed; read-error behavior follows [failure isolation](../../server/engine/pull.md#9-architecture-decisions).

## 11. Risks and Technical Debt

**Accepted limitation (planned change).** `watch` re-runs its query on every commit, whatever table changed: the rule now belongs to the [runtime](../../client/runtime.md#11-risks-and-technical-debt), which keeps it for every language. Scoped notifications are [#16](https://github.com/zanminwang/axton/issues/16).

**Accepted limitation.** `Client.open` and the generated `open` still accept a `migration` option that the runtime ignores; its future is part of [#20](https://github.com/zanminwang/axton/issues/20).

**To confirm.** No test runs one script through the Rust, TypeScript and Dart clients and compares state. Both SDKs now drive the same Rust runtime, and the shared envelope fixtures check that their Bridges read and write the same messages, but each still has its own typed API, effect executors and transport, so sharing the runtime alone does not establish equivalent behavior across SDK boundaries. The shared scenarios in `fixtures/scenarios` are prose READMEs, not an executable cross-language runner.
