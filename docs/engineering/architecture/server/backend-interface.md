# Backend interface

## 1. Introduction and Goals

The backend interface is where the framework meets application code. The Rust engine never touches the application's database directly; instead it asks a *host* to do things, and the host runs each request inside the transaction the application opened. Two of those requests reach application code: run this handler, load these records.

## 3. Context and Scope

**Operation host contract.** The generated backend registers one handler for each retained Mutation or Query version, under `mutations` or `queries` by that version's kind. The host invokes it with `{ctx, args}`: a Mutation's `ctx` contains the application transaction, authenticated user, stable call ID, `invalidate` and `stream(name)` (section 6); a Query's `ctx` contains only the transaction, user and call ID, and the host answers its `handle` with empty changes and memberships. `args` is decoded from the retained input snapshot. The handler returns explicit scalar/enum values and identity objects for explicit Model outputs, and nothing else: no output is inferred from an input, whatever its name. The shared executor refuses a Query settlement carrying changes or memberships with `query.effects_forbidden` whatever host produced it, before any stamp, readback or publication ([enforcement and its limit](../schema/actions.md#8-crosscutting-concepts)). It resolves Model outputs through the appropriate retained Loader version. The handler's output snapshot is distinct from the batch-final input readback. See [server execution](engine/README.md) and [typed server API](../sdks/typed-api/server.md).

**Load host contract.** Each retained Load version registers under `loads`, receives `{ctx, args, continuation}` and returns `{data, next}`. `ctx` contains the application transaction, user, page call ID, load ID and `stream(nameOrNames).track` only. Every tracked identity must be returned by the page; limits apply after Cartesian expansion. The collector remains failed after a refused declaration even if caught. Data, tracking and the saved page commit together. Saved replay runs no handler, Loader or declarations. See [Loads](engine/loads.md) for continuation and failure classification.

`CallRejected(code)` is the public backend business-rejection class for both kinds; it has the same explicit code semantics as the retained legacy `MutationRejected` path described below. A handler or Loader exception that is not a business rejection becomes `handler.failed` or `loader.failed` for that call unless it is a retryable database transaction error. A persistence fault aborts the outer transaction for retry. Diagnostic callback exceptions after commit are reported through the SDK runtime uncaught-error channel and cannot replace the committed outcome.

The host operations the engine may issue:

| Operation | Answered by | Purpose |
| --- | --- | --- |
| `handle` | the application's handler | run one mutation's business logic |
| `handleLoad` | the application's Load handler | enumerate one Load page's identities and next continuation, with any Stream additions it declared (no changes) |
| `load` | the application's loader | return the current state of records |
| `savepoint`, `rollback`, `release` | [Persistence](persistence.md) | isolate one mutation's effects |
| `claim`, `saveReceipt`, `head`, `scan` | [Persistence](persistence.md) | client rows, receipts and the invalidation table |
| `advanceStamp`, `ensureStamp`, `readStamps` | [Persistence](persistence.md) | record stamps ([Publish](engine/publish.md)) |
| `readTracking`, `guardRecords`, `lockStreams`, `applyStreamMembers` | [Persistence](persistence.md) | bulk tracking reads/record guards, Stream locks and positions |

Each operation is one variant of `HostRequest` with one response type, defined once in [server/host.rs](../../../../crates/server/src/host.rs) and restated for TypeScript in [server/host-contract.mts](../../../../packages/server/host-contract.mts) (section 9). [fixtures/protocol/host-operations.json](../../../../fixtures/protocol/host-operations.json) carries one example of every request and every response variant, and both hosts are tested against it.

Application-facing contracts ([Typed API / Server](../sdks/typed-api/server.md) shows their types):

- A legacy slot **handler** receives `{input, tx, userId, stream, invalidate}`: the decoded input (one value per slot), the transaction, the user id and the same declaration handles an operation handler has. The records the uploaded operations target are already the mutation's changes; `invalidate.todo(identity)` reports a record the handler changed beyond them, and `stream(name).track.todo(identity)` establishes durable interest. Its return value is ignored. Throwing `MutationRejected`, or an error `translateRejection` maps to a code, rejects that one mutation; any other error rejects that same mutation with `handler.failed` and is reported to `onError` — the rest of the batch still runs and commits ([#95](https://github.com/zanminwang/axton/issues/95)). What the framework does with the change set after the handler returns is [Push](engine/push.md).
- A **loader** serves one retained model read contract (a model name and version) and receives `{ids, tx, userId}`: identities, the transaction and the user id, never a stream. A Model without one is device-only (section 5). It returns one row or `null` per identity, in order, shaped as that version's records. `null` means "not visible or deleted" and is delivered as a delete; a missing entry or `undefined` is a defect. Throwing `MutationRejected` (or an error `translateRejection` maps) refuses the read; any other error is a failure and is reported to `onError`. Inside a push either rejects the mutation being read back (with the refusal code, or `loader.failed`); in a pull either becomes that record's `error` change and the rest of the page is served ([Server / Engine / Pull](engine/pull.md)); in a native Load page a refusal is the page's saved rejection with its code, a failure its `loader.failed`, and a `null` its `load.record_unavailable`, never a deletion ([Server / Engine / Loads](engine/loads.md#6-runtime-view)). A client's **Model Fetch** (`POST /sync/fetch`, [#153](https://github.com/zanminwang/axton/issues/153)) calls the same Loader once for one identity at the requested retained version: a row is the result, `null` is absence (stored by a storing client as a deletion), and a refusal, failure or invalid row is the call's saved rejection, which deletes nothing. Fetch needs no Handler registration and adds no host operation; it uses `claimCall`/`saveCall`, the savepoint operations, `ensureStamp` (only when storing, before the read, so a stamp row remains even for an identity the Loader answers `null`) and `load`; `saveCall` keeps the full snapshot for replay, `store: false` included ([Protocol / Direct calls](../protocol/actions.md#model-fetch)). Without an `onError` option, errors are logged with `console.error`.
- `authenticate(request)` returns the user id or null. Handlers and loaders own application authorization; the framework does not enforce stream-level policy ([#22](https://github.com/zanminwang/axton/issues/22)).
- The application also owns unique and identity constraints on the server, child deletion (`onTargetDelete` is a client-side cascade), and one local database per signed-in user; the backend is TypeScript on Node only, and prerequisite arguments are `self` only. These accepted limits are stated for authors in [What your backend owns](../../../../website/docs/backend/api.md#what-your-backend-owns).

## 5. Building Block View

Startup validates the compiled config and requires a handler for every retained version of a slot mutation (under `handlers`) or an operation (under `mutations` or `queries`, by that version's kind), and, for each Model that registers a loader, one for every retained version of that Model; a missing, extra or wrong-kind registration, or a loader key that names no Model, makes `createBackend` throw. The engine decodes the config's `models` list (every retained model read contract, `{name, version, identity, fields, enums}`) into one normalization schema per version, refusing a contract whose identity differs from the model's, a duplicate version, an invalid field or enum, and a schema whose current version is not retained; a hand-written config without `models` retains each model at the schema's own version. A mutation's handler key and a model's loader key are `lowerFirst(name)`; each value holds a `v<n>` member per retained version, and a contract retaining only v1 also accepts the bare function ([Typed API / Server](../sdks/typed-api/server.md#9-architecture-decisions)).

**Device-only Models ([#187](https://github.com/zanminwang/axton/issues/187)).** A Model whose loader is omitted (absent or `undefined`) is device-only. `createBackend` passes the engine only the Models with a loader as the config's `loaders`, and the engine's `Config::decode` refuses, with `config.invalid`, a retained descriptor that would need the missing loader: a slot mutation's slot or a Mutation's Model operand (`Mutation SaveDraft v1 slot draft names Model Draft, which has no Loader; …`), or a Mutation, Query or Load Model output (`Query FindDrafts v1 output drafts names Model Draft, …`). A device-only Model is never published: the declaration collector shared by handlers, `backend.transaction` and `backend.publish` throws at `invalidate.draft`, `stream(name).track.draft` or a mixed `stream(name).track` naming it (`invalidate.draft: Model Draft has no Loader, so it is device-only and cannot be published`), and every engine path that would read, settle or publish it (settlement, readback, pull, Fetch, Load pages) refuses it with `loader.unregistered`, whose message names the Model, for any host. Client-side writes to such a Model are ordinary local writes and never reach the wire.

At runtime the host function shapes handler input from the engine's decoded arguments: a create slot becomes `{…identity, …data}`, an update becomes `{identity, patch}`, a delete becomes `{identity}`; list slots are arrays and optional slots may be `null`. These are plain data: a declaration takes the record itself for a create and `input.todo.identity` otherwise, and copies only the identity fields.

A per-transaction **session** tracks every host callback promise. It records the first failure, refuses to let the transaction commit while callbacks are unfinished or failed, and snapshots the set of streams published to around each mutation's savepoint so a rejected mutation wakes nobody ([Publish](engine/publish.md)). `backend.transaction` runs application code outside a push on the same machinery, with `settle_external` in place of `handle` and `load`; `backend.publish` binds the same session to a transaction the application opened, for one settlement ([Publish](engine/publish.md#9-architecture-decisions)).

Code: the operation contract in [server/host.rs](../../../../crates/server/src/host.rs) (`HostRequest`, the response types, `HostExt::call_typed`) and the `Host` trait in [server/lib.rs](../../../../crates/server/src/lib.rs); on the TypeScript side the same contract in [server/host-contract.mts](../../../../packages/server/host-contract.mts) and `createBackend`, `host`, `Session` in [server/index.mts](../../../../packages/server/index.mts), with the persistence half answered by [packages/postgres/src/persistence.mts](../../../../packages/postgres/src/persistence.mts) over a two-method driver ([Persistence](persistence.md)). The simulation implements the same operations in memory in [crates/sim/src/host.rs](../../../../crates/sim/src/host.rs).

## 6. Runtime View

The callback-bound collector provides `stream(...).track`, global `invalidate` and selected `stream(...).invalidate`; typed/mixed calls copy and canonicalize operands before appending. Handles expire with their callback. Declarations combine in one settlement; invalid ordinary declarations append nothing, while Load collectors retain sticky failure. The engine owns fan-out, stamp allocation and conflict detection. [Publish](engine/publish.md) owns settlement order and callback lifetimes. Queries and viewer Loaders cannot declare either verb.

## 9. Architecture Decisions

The [Rust host contract](../../../../crates/server/src/host.rs) defines typed requests and responses; [TypeScript host-contract.mts](../../../../packages/server/host-contract.mts) mirrors it. The [conformance fixture](../../../../fixtures/protocol/host-operations.json) covers both sides. Unknown fields and malformed responses fail their existing operation error boundary.

| Operation | Request / response |
| --- | --- |
| `readTracking` | `{records: MemberKey[], pairs: TrackingPair[]}` → union of all holders for named records and existing explicit pairs, without duplicates. `MemberKey = {model, identityKey}`; `TrackingPair` adds `stream`. |
| `guardRecords` | Canonical `{model, identityKey, mode: "advance" \| "ensure" \| "lock"}[]` → request-aligned positive safe stamps; only lock may return null. |
| `lockStreams` | Distinct names in canonical byte order → null; Stream locks precede record guards. |
| `applyStreamMembers` | Final `{stream, model, identity, identityKey, publish}` pairs → matching `{stream, model, identityKey, cursor, kind}` positions. No label or withdrawal declaration. |

Tracking and invalidation are the two application verbs; native Loads provide tracking only. Historical removal positions are still scanned and decoded. [Persistence](persistence.md) owns storage and bounded SQL; [Publish](engine/publish.md) owns declaration combination and whole-transaction retry. A Model without a registered viewer Loader is device-only and cannot appear in wire operands, outputs or declarations.

## 10. Quality Requirements

Handlers settle effects, reject or fail within their savepoint. Queries and viewer Loaders have no declaration surface. Native Load declarations target only page output and fail atomically. Viewer Loader errors never become null authority. Models without Loaders are device-only. See [host conformance](../../../../crates/server/tests/host_contract.rs), [declaration collector tests](../../../../integration/persistence/server/effects.test.mjs) and [runtime integration](../../../../integration/persistence/server/runtime.test.mjs) for coverage; test execution belongs in task evidence.

## 11. Risks and Technical Debt

**Resolved: the host operation set was an untyped string contract implemented three times.** Section 9 landed ([#45](https://github.com/zanminwang/axton/issues/45)): `host.rs` is the one definition, `host-contract.mts` restates it for TypeScript, and the shared fixture fails whichever side drifts. What remains is the hand-written mirror — the two languages have no shared generator, so adding an operation still means editing `host.rs`, `host-contract.mts` and the fixture; the compiler and the two conformance tests catch a half-done edit, they do not spare it.

**Contract ownership.** Rust and TypeScript mirror the bulk host operations explicitly; new fields require updating both and the conformance fixture. [Publish](engine/publish.md) owns current settlement semantics.

**Accepted limitation.** A loader must return exactly its version's contract fields: identity fields may be present, an absent nullable field reads as `null`, an absent non-nullable field or any extra property fails normalization: in a pull that record is a `loader.invalid` change, in a push that mutation is rejected with `loader.invalid`, and either way the host reports it to `onError`. Evidence: `normalize_state` over the retained contract in `process_pull`; the loader-defect test above and `a pull reaches the loader of the declared model version and normalizes rows with that contract`. Documented for authors under [Loaders](../../../../website/docs/backend/api.md#loaders).
