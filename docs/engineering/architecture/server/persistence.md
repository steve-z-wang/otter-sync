# Persistence

## 1. Introduction and Goals

Persistence stores the framework's tables in the application's own database, through the application's own transaction. That is what makes a push atomic: business writes, stamps, publications and receipts commit together. PostgreSQL is the database; the application chooses the tool it talks to PostgreSQL with.

## 3. Context and Scope

`@axtonjs/postgres` ([packages/postgres](../../../../packages/postgres)) owns every SQL statement AXTON runs, the migration, and the driver interface a PostgreSQL access tool binds. `packages/server` knows no SQL: `createBackend({database})` takes a `Database<T>`, a `transaction(body)` runner plus a `persistence(tx)` factory whose `call(request)` answers the host operations below, and `@axtonjs/postgres` builds that object from a driver.

```ts
interface PostgresDriver<Tx> {
  transaction<R>(body: (tx: Tx) => Promise<R>): Promise<R>; // SERIALIZABLE, retry 40001/40P01
  query(tx: Tx, sql: string, params: readonly unknown[]): Promise<Record<string, unknown>[]>;
}
```

| Request | Meaning |
| --- | --- |
| `claim {owner, clientId}` | create the client row if new, lock it, return owner, sequence and stored receipt |
| `saveReceipt {owner, clientId, sequence, receipt}` | record the batch outcome |
| `claimCall {owner, callId, request}` | insert or lock a call; return whether this transaction inserted it plus its immutable request and saved response |
| `saveCall {owner, callId, response}` | complete a fresh, uncompleted call claimed by the current transaction |
| `head {scope}` | current cursor of a scope (0 if unknown) |
| `scan {scope, after, limit}` | the Scope's retained `upsert` and `remove` log rows after a cursor, limited after both kinds are selected, in order; every row carries record identity, and only an upsert requires the current positive stamp; missing record metadata is a storage defect |
| `advanceStamp {model, identityKey}` | allocate the record's next stamp (1 for a record without one) and return it |
| `ensureStamp {model, identityKey}` | return the record's current stamp, initializing it at 1 only when it has none |
| `readStamps {model, identityKeys}` | return the current stamps of many records of one model in request order: existing rows are read, never rewritten or locked, and only missing ones are inserted at 1 (`INSERT … ON CONFLICT DO NOTHING` in a CTE, so a row committed after the snapshot fails serialization and the runner retries). Each stamp is looked up by its key; a missing row or an invalid stamp answers `null` in its position and an impossible request answers `[]`, which the engine refuses as `host.invalid` rather than retrying |
| `lockRecord {model, identityKey}` | write-lock an existing record row with a no-op `UPDATE … SET stamp=stamp` and return its unchanged stamp; `null`, creating nothing, when the record has no row |
| `memberships {model, identityKey}` | the Scopes the record is a persistent member of, each once, in the database's order (the engine sorts them) |
| `lockScopes {scopes}` | lock each existing Scope row in exactly the given order (`SELECT … ORDER BY ordinality FOR NO KEY UPDATE`) and give it a new row version with a no-op `UPDATE`, so a concurrent Scope writer whose snapshot predates the commit retries; create none |
| `readScopeMembers {scope, explicitKeys, tags, all?}` | the live members the keys name (in any order, repeats allowed) or a tag selects, or every live member when `all: true`, each once with its complete tags |
| `applyScopeMembers {deltas}` | write final member states and tags without re-evaluating selectors, reserve one consecutive cursor range per Scope for the published deltas, and answer one position per delta: new for a published one, existing for a kept one |
| `savepoint`, `rollback`, `release {ordinal}` | per-mutation savepoints |

Tables ([migration.sql](../../../../packages/postgres/migration.sql)): `axton_client`, `axton_call`, `axton_scope`, `axton_record` (surrogate `id`, unique `(model, identity_key)`, and `identity` generated from the canonical key), and the Scope tables: `axton_scope_member` (live members only, unique `(scope, record_id)`, indexed `(record_id, scope)` for touch fan-out), `axton_scope_tag` (unique `(scope, name)`), `axton_scope_member_tag` (keyed `(member_id, tag_id)`, indexed `(tag_id, member_id)` for selectors, cascading from both sides) and `axton_scope_log` (one row per pair, keyed `(scope, record_id)`, unique `(scope, cursor)`, kind `upsert` or `remove`). A constraint trigger refuses an association whose member and tag belong to different Scopes, and update triggers keep a member's or tag's Scope fixed. Members and log rows reference `axton_record` without cascading, so record metadata stays while either refers to it; no log row is ever pruned. The shared settlement issues `lockScopes`, `lockRecord`, `memberships`, `readScopeMembers` and `applyScopeMembers` ([Publish](engine/publish.md#5-building-block-view)). A 0.1.x database upgrades with [migrations/2026-09-30-channel-members.sql](../../../../packages/postgres/migrations/2026-09-30-channel-members.sql): one transaction that adds record IDs, copies memberships, turns each retained invalidation into a log row at its cursor (`upsert` for a live member, `remove` otherwise), gives members never published an `upsert` above their Scope's head in record-key order, and verifies the result. It keeps `axton_membership` and `axton_invalidation`, fails whole on an identity that disagrees with its key or any inconsistency, and copies only while `axton_record` has no `id`, so a repeated run only verifies.

## 5. Building Block View

| Module | Owns |
| --- | --- |
| [src/driver.mts](../../../../packages/postgres/src/driver.mts) | `PostgresDriver<Tx>`, `DriverOptions {retries, timeout}`, `withRetries`, `retryDelay` and its `RETRY_BACKOFF_BASE_MS`/`RETRY_BACKOFF_CAP_MS`, `RETRYABLE_SQLSTATES` |
| [src/sql.mts](../../../../packages/postgres/src/sql.mts) | every statement, as named constants; the only place SQL text lives |
| [src/persistence.mts](../../../../packages/postgres/src/persistence.mts) | `answer(driver, tx, request)`, the switch over the operations above, and `persistence(driver)`, the `Database<Tx>` it becomes |
| [src/pg.mts](../../../../packages/postgres/src/pg.mts), [src/prisma.mts](../../../../packages/postgres/src/prisma.mts), [src/drizzle.mts](../../../../packages/postgres/src/drizzle.mts) | the shims: `pg(pool)`, `prisma(client)`, `drizzle(db)`, each binding the two methods to its tool's transaction |

Properties the SQL holds: `claim` uses `SELECT … FOR UPDATE`, so retries of one client serialize on the row; `claimCall` uses `INSERT … ON CONFLICT DO NOTHING RETURNING` followed by `SELECT … FOR UPDATE` in the supplied transaction, so a duplicate sees the original request and response after the first transaction commits. A committed null response is a storage fault. `saveCall` checks the full creating transaction ID (`claim_tx`) and refuses overwrites. No call responses are automatically pruned. `advanceStamp` and `ensureStamp` allocate stamps with atomic upserts that return the new value, so concurrent first publications agree on 1 and an established stamp is never overwritten; `scan` filters `kind = 'upsert'` before `ORDER BY … LIMIT` and is a `LEFT JOIN` from the log row to the record row, so a page carries the stamp of the content the loader reads. `applyScopeMembers` runs fixed statement groups, each binding at most three parameters as JSON arrays of at most `CHANNEL_BATCH` (1,000) entries, inside the caller's transaction: one `INSERT … ON CONFLICT DO UPDATE` reserving every Scope's range (a missing Scope is inserted, so two first writers serialize on its primary key; a head that would pass 2^53−1 is not updated and the call fails before commit); then per batch the log upsert, which also reads kept deltas' positions in the same pass; the member insert and the tag set (create missing tags, drop and add associations); the member deletion; and finally the deletion of tags left without members. Removing 10,000 tagged members takes 24 statements and no Loader call. `lockRecord` is an `UPDATE`, not `SELECT … FOR UPDATE`: under a transaction snapshot, a row a concurrent committed transaction only locked can still be written from an older snapshot, while a row it updated makes that write fail serialization, so the runner retries it. The shims' Serializable level already rules out a non-serial outcome on its own; the guard keeps the conflict in a caller-owned transaction at Repeatable Read (`backend.publish`). Counters are `bigint` with safe-range checks and are narrowed to safe integers on the way out; a driver whose tool cannot send a bigint parameter sends it as text.

Each shim's `transaction` runs at Serializable and retries serialization failures (`40001`, `40P01`; Prisma `P2034`, or `P2010` with one of those codes in `meta.code` or, from a Prisma 7 driver adapter, in `meta.driverAdapterError` as a `TransactionWriteConflict` or PostgreSQL error) a bounded number of times, re-running the whole body. Before each retry `withRetries` waits a random delay below `min(400, 20 × 2^n)` milliseconds for retry `n` (full jitter, `retryDelay`), so transactions that failed together do not restart together; with the default three retries the waits total under 140 ms. `pg` opens `BEGIN ISOLATION LEVEL SERIALIZABLE` on a pooled client; `prisma` uses `$transaction(body, {isolationLevel: 'Serializable', timeout})` and `$queryRawUnsafe`; `drizzle` uses `db.transaction(body, {isolationLevel: 'serializable'})` and rewrites `$n` placeholders into a `sql` template (`bindDrizzle`) so the tool binds the parameters itself.

Serializable keeps Repeatable Read's single snapshot per transaction, which the bookkeeping above relies on (`ensureStamp`, `readStamps`, `lockRecord`, and head, scan and load reading one state), and additionally makes PostgreSQL abort, with `40001`, a transaction whose outcome no serial order would produce. A handler therefore needs no locks for correctness, and its body may run more than once ([guarantees T1–T2](../../guarantees.md#t-backend-transactions)). There is no option to choose another level.

Code: [packages/postgres/index.mts](../../../../packages/postgres/index.mts); the `Database<T>` contract in [server/index.mts](../../../../packages/server/index.mts), which requires serializable isolation of any runner.

## 9. Architecture Decisions

**One package for PostgreSQL, a two-method driver per tool ([#103](https://github.com/zanminwang/axton/issues/103), decided 2026-09-16).** Modelled on River: the database is fixed, the driver is small, the transaction is the application's. Every statement lives once, in `sql.mts`, and a tool shim only binds `transaction` and `query`, so supporting another PostgreSQL tool is thirty lines and the same conformance suite; handlers and loaders keep receiving their tool's own transaction. A different database would be a different package, not a driver, and is not planned. The former `persistence-prisma` package became the `prisma` shim.

**Every shim transaction is Serializable ([#202](https://github.com/zanminwang/axton/issues/202), decided 2026-09-28).** Under Repeatable Read a handler that locked a parent row and then re-checked its children read the snapshot taken before its lock wait, and committed decisions on rows another transaction had already deleted or created. Read Committed would fix the re-check but break the one-snapshot bookkeeping above; Serializable keeps that snapshot and turns the stale decision into a retried `40001`. No option chooses another level. The cost is more retries under contention, bounded by `retries`, and the requirement that handler bodies are safe to run again ([design](../../../superpowers/specs/2026-09-28-202-serializable-transactions-design.md)).

## 10. Quality Requirements

- **Every shim answers the persistence operations the same way against a real database** (claim creates and locks the row and replays the stored receipt; owner mismatch refuses; `head` is 0 for an unknown scope; `advanceStamp` 1, 2 and `ensureStamp` agree on 1 under three concurrent transactions; `applyScopeMembers` reserves one consecutive range per Scope, answers kept positions and refuses a record without metadata; a rolled-back transaction removes a first initialisation; `scan` answers both kinds before its limit, joins identity/current upsert stamp and reports missing metadata; savepoints roll back and release; a serialization conflict retries the whole body). Evidence: [driver-conformance.test.mjs](../../../../integration/persistence/server/driver-conformance.test.mjs), run once each for `pg`, `prisma` and `drizzle`, and the `pgDriver` retry unit test in the same file.
- **Each call claim and response share the application's transaction with business writes.** Concurrent duplicate claims execute the body once; rollback removes both records; a different owner sees a separate claim; changed intent returns the immutable original; a committed null response and a second save are refused. A fresh claim created under an ambient savepoint can be saved after release. Evidence: [driver-conformance.test.mjs](../../../../integration/persistence/server/driver-conformance.test.mjs), run against `pg`, `prisma` and `drizzle`.
- **Concurrent retries of one client execute once; head, scan and loader see one snapshot.** Evidence: [runtime.test.mjs](../../../../integration/persistence/server/runtime.test.mjs) `concurrent same-client retry executes once under PostgreSQL lock`, `the serializable runner keeps head, scan, and loader coherent across concurrent publication`.
- **Two racing lock-then-recheck transactions that each read or write the other's rows cannot commit a non-serial outcome: exactly one retries, and the final state is a serial one** ([guarantee T1](../../guarantees.md#t-backend-transactions); some serial order, not the real-time commit order, and only when both sides touch the rows involved). The delete case: one transaction locks a parent, deletes a child and its dependent rows, while another, whose snapshot predates that commit, locks the same parent, re-checks the child and writes a dependent row for it. The insert case: one transaction locks a parent and inserts a child, while the other locks it, deletes its children and then the parent. The two are ordered by promises alone. Evidence: [driver-conformance.test.mjs](../../../../integration/persistence/server/driver-conformance.test.mjs) `lock-then-recheck, delete case: an Archive for an Author who already left never commits; exactly one transaction retries`, `lock-then-recheck, insert case: a delete's cleanup never misses a Star created at the same moment; exactly one transaction retries`, run against `pg`, `prisma` and `drizzle`; `control: at Repeatable Read both lock-then-recheck races commit on a stale re-check` shows the same races commit the stale decision at the former level.
- **A stamp advances without a scope; one push publishing to two scopes carries one stamp to both and advances each head once; an external write advances the stamp on every call while a push publishing an unchanged record does not; concurrent first publications initialize one stamp of 1; a rolled-back transaction removes a first initialization with its publication; `applyScopeMembers` refuses a record without metadata and a kept member without a position; `scan` pairs the cursor with the current stamp** (guarantee D3). Evidence: `advanceStamp increments without a scope: no invalidation, no scope head`, `one push enrolled in two scopes carries the same stamp to both and advances each head once`, `an external write advances the stamp on every call; a push re-enrolling an unchanged member neither advances nor publishes it`, `concurrent first publications initialise one stamp of 1 and never overwrite an established one`, `a rolled-back transaction removes a first initialisation together with its publication`, `applyScopeMembers refuses a record without metadata and a kept member without a position`, `scan pairs the invalidation cursor with the current record stamp; a missing record row is a storage defect`, `concurrent notifies of one record receive distinct stamps`.
- **Membership is persistent, idempotent and separate from publication; a record guard makes a stale-snapshot writer retry.** `applyScopeMembers` needs the record row; `lockScopes` creates no Scope; a first member creates its Scope with the first position, a kept member moves no head and a removal takes a position; `readScopeMembers` answers named and tagged members once with complete tags; memberships, tags, positions and heads roll back with a savepoint or transaction; `lockRecord` answers `null` without creating a row and preserves the stamp. A writer whose snapshot predates a committed membership-only transaction (`lockRecord` then `applyScopeMembers`) fails serialization when it writes the record and its retry reads the new membership. At the shims' Serializable level it restarts even without the guard. When the enrolling transaction is a caller-owned one at Repeatable Read and the writer a shim's, only the guard's row write makes the writer restart; without it, or with `SELECT … FOR UPDATE` in its place, the writer commits on the stale view. Evidence: [driver-conformance.test.mjs](../../../../integration/persistence/server/driver-conformance.test.mjs) `Scope operations add, read and remove members idempotently, need record metadata and create no Scope before a position`, `savepoint and transaction rollback restore members, tags, positions and heads`, `applyScopeMembers reserves one consecutive range per Scope in delta order, answers a kept member's position and refuses a record without metadata`, `a membership-only writer's no-op record UPDATE makes a stale-snapshot writer of the same record retry`, run against `pg`, `prisma` and `drizzle`.
- **Membership filtering, removal and concurrent declarations hold on a real database.** A removal replaces the pair's position with a `remove` above the head, which scope delta and Bootstrap pages deliver as identity-only release; re-adding publishes current state at a fresh position without a new stamp; a deleted member yields `null` and its recreation is distributed again; removal fabricates no deletion and keeps business rows and stamps. Touch/add and touch/remove race in both commit orders with the final stamp on the enrolled Scope and release evidence on the removed one; membership-only races keep the stamp and a duplicate add publishes once; a call rejected after settlement and a failed transaction roll back relationships, stamps, heads and wakes, and the retried batch settles once. Evidence: [membership.test.mjs](../../../../integration/persistence/server/membership.test.mjs), every test in the file, over the `pg` shim.
- **Tags, synchronized removal, the schema and the upgrade hold on a real database.** A pair is one member whose adds union their tags, with no position for a tag-only change; same-named tags of two Scopes are distinct rows; removing a tag removes whole memberships (after removing X from A (X, Y) and B (X), the Scope has no member and no association and its log two `remove` rows), calls no Loader and collects unused tags; removing an absent record or unmatched tag allocates nothing; the log keeps one row per pair; a rolled-back or failed settlement leaves every table as it was, including a failure injected after the log writes of a 10,000-member removal. Direct SQL shows the association trigger, fixed Scope ownership, the unique keys and the counter bounds; a head that would pass 2^53−1 fails before commit. Add versus tag removal, tag union versus an empty selector, touch versus tag removal and two first writers of a new Scope, released together behind a barrier, each commit one serial outcome with exactly one retried transaction and no extra cursor. The upgrade from the six-table schema converges with a fresh install (columns, constraints, indexes, triggers and functions), keeps the old tables, maps retained positions and allocates unlogged members' positions as specified, is a verified no-op when repeated (no row rewritten, even after runtime writes) and fails whole on inconsistent data. Removing 10,000 tagged members runs 24 statements. Evidence: [scope-tags.test.mjs](../../../../integration/persistence/server/scope-tags.test.mjs), over the `pg` shim.
- **Fresh framework tables define no `request_hash`; a table installed from an earlier `migration.sql` that still carries the column serves claim, replay and gap checks unchanged, before and after the column is dropped.** Evidence: `fresh framework tables omit request_hash; a table that still carries the column keeps replaying receipts`.
- **Per-mutation savepoints behave as savepoints against a real database.** Evidence: [transaction-bridge.test.mjs](../../../../integration/bindings/node/transaction-bridge.test.mjs) `business rejection rolls back its savepoint while preceding mutation commits`.

Executed 2026-09-30 with PostgreSQL 14.23: `bash integration/persistence/server/run.sh` (effects, driver-conformance, runtime and host-contract, actions, membership, loads, fetch and scope-tags suites all passing, the conformance races at Serializable included).

## 11. Risks and Technical Debt

**Accepted limitation (legacy column).** `axton_client` once defined a `request_hash text` column that nothing wrote or read; receipt replay is keyed by client and sequence ([Server Push §9](engine/push.md#9-architecture-decisions)). Databases installed before its removal keep the column: `CREATE TABLE IF NOT EXISTS` never alters an existing table, and the statements name their columns, so the extra one is ignored. Removing it is optional and safe, `ALTER TABLE axton_client DROP COLUMN request_hash`, and touches no receipts or business data.

**Accepted limitation: no transaction timeout with `pg` or `drizzle`.** `DriverOptions.timeout` applies only where the tool supports one, and their `transaction` runners set none: a hung application transaction holds its claim row, and a resend of the same call ID - a native Load page in particular ([Server / Engine / Loads](engine/loads.md#11-risks-and-technical-debt)) - blocks behind it. The `prisma` shim passes its `timeout` (20 s by default).

**Accepted limitations.** PostgreSQL is the only database. The framework tables are installed from a raw SQL file with no migration tooling. Rows are never pruned: client rows live forever and Scope log rows grow with every record ever represented in a Scope, removals included ([#61](https://github.com/zanminwang/axton/issues/61)). The isolation requirement on a driver's runner is stated in the interface's doc comment and checked by the conformance race tests, not enforced at runtime: a hand-written driver or a caller-owned transaction at a weaker level is not detected. **Known risk: retries under contention at Serializable.** Conflicts come not only from rows another transaction writes but from shared index pages: PostgreSQL's predicate locks on a small index cover whole pages, so on near-empty framework tables concurrent transactions on disjoint rows (a call claim, two new stamps, the saved call) abort each other. Measured 2026-09-28 on PostgreSQL 14.23 with the `pg` shim and the default three retries, 50 rounds of concurrent calls each: without a wait between attempts, 198 of 400 calls exhausted their retries at concurrency 8 and 270 to 282 of 400 at 16; with the jittered wait, 0 to 5 of 400 at 8 and 14 to 25 of 400 at 16, at about 2.3 attempts per call; with 100,000 rows in `axton_call` and `axton_record`, 0 of 400 either way. An exhausted call is a retryable server failure and is resent (T2), so the cost is latency and load, not lost work. Follow-up: [#210](https://github.com/zanminwang/axton/issues/210), under [#12](https://github.com/zanminwang/axton/issues/12).

A multi-Mutation push can acquire later settlement locks after earlier ones: deadlock remains possible and requires bounded whole-transaction retry. Additive migration retains old tables and log tombstones; even repeated migration takes an `ACCESS EXCLUSIVE` record-table lock. No TTL or pruning floor ships with this capability.

## Scope forward migration

With old writers stopped, existing v0.2 metadata applies [2026-09-30-scopes.sql](https://github.com/zanminwang/axton/blob/main/packages/postgres/migrations/2026-09-30-scopes.sql) before the current DDL. A v0.1 database applies the historical `2026-09-30-channel-members.sql` first, then the Scope migration; never reapply that historical migration after cutover. Fresh DDL refuses installed old layouts. The forward transaction renames framework tables, columns and schema objects, and rewrites framework claims in saved outcomes, preserving application payloads, opaque Scope values, stamps and progress. It is idempotent and rolls back wholly on inconsistency. See [coordinated cutover](https://github.com/zanminwang/axton/blob/main/website/docs/backend/deployment.md#scope-membership-cutover).

Selection reads named identities, referenced labels, and all members when required for negation or unlabelled matching; the Rust reducer evaluates ordered predicates over complete label sets. Label-only edits allocate no stamp or cursor, invoke no Loader and emit no event. Custom hosts must implement this read/lock/reduction boundary.
