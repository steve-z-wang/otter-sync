# Guarantees

The behavioral contract of the Rust sync core. These are requirements, not a claim that every case is implemented or tested. [Coverage review](testing/review.md) records known gaps and decisions still needed; [component documentation](architecture.md) owns API, encoding, schema and adapter rules.

Simulation exercises these behaviors across clients and message sequences. Real-database tests must also verify claims that depend on persistence or transaction semantics. IDs remain stable so scenarios can refer to them. Existing references to a mutation describe the retained queue and replay machinery; generated application APIs expose Mutations and Queries for backend work and local-only Model CRUD for local writes.

## Failure isolation

Applications use individual operations as they would ordinary API calls. This applies to mutations and loader reads: a failure attributable to one operation must be reported for that operation, without rejecting or blocking unrelated work merely because it shares a batch, page or scope. Explicit application transactions, including an incoming-authority `onStore` callback, and declared dependencies still define shared outcomes. A callback shares the enclosing local storage transaction: its failure rolls back that unit and may cause delivery retry or block its Scope or frozen batch if it keeps failing. This does not change isolation of known per-record loader/validation failures, which are identified before callbacks. Transport or database transaction failure may require retrying delivery; it must not be reported as business rejection of every operation in that delivery.

A native Load page is one operation in this sense: its declared output is applied completely or not at all (N2), so a record failure fails that page, while sibling Loads that share its HTTP batch are unrelated work. The per-record isolation of D7 belongs to Scope delivery and Bootstrap and is unchanged.

## L. Local writes

| ID | Required behavior |
| --- | --- |
| L1 | Reads show the authoritative base with pending local edits replayed in order. A transaction sees its own writes; other readers see them after commit. |
| L2 | Committed records, queued mutations and rejections survive database reopen. |
| L3 | A failed transaction rolls back its changes. A nested savepoint can roll back its own scope without discarding the outer transaction. |
| L4 | Direct writes are device-only: they never enter the push queue, including writes to a Model that Scopes deliver. Companion edits follow their mutation's acceptance or rejection at their place in local order: apart from server authority for the record, settling a mutation neither undoes nor reorders a later direct write or a later mutation's companion, whatever order the outcomes arrive in. Direct edits to an authoritative record survive rejection of a pending mutation, which removes only that mutation's optimism, companions included. Newer authority for the record replaces them, and nothing replays them afterwards. Newer means a stamp above the one the client holds, whether a receipt, a Scope page, a Load page or a Fetch delivers it. A record whose create is still pending has no authoritative base: if the create is rejected the record goes, direct edits included. A page the client has already applied does not undo a direct edit. |
| L5 | Local deletion applies the cascades declared by the schema, with the same rollback scope as the initiating operation. |

L4 is pinned for each canonical source: a Scope page, a Load page and a Fetch ([#188](https://github.com/zanminwang/axton/issues/188)). An application can therefore store canonical data from another transport with a direct write, and the next newer delivery of that identity replaces it. Evidence: [sqlite/tests/direct_writes.rs](../../crates/sqlite/tests/direct_writes.rs) `a_direct_write_is_never_queued_and_newer_canonical_data_replaces_it`, `a_refused_mutation_leaves_a_direct_write_on_its_row`, `after_a_refusal_newer_canonical_data_replaces_the_surviving_direct_write`, `canonical_data_during_a_pending_mutation_retires_the_direct_write_for_good`. A redelivery at the stamp the client already holds is not newer authority. When a direct write has changed that record, the redelivery is an equal-stamp conflict (D8). A Scope page reports it and keeps the direct write. A Load page (N2) or a Fetch that carries it is refused whole. `an_equal_stamp_redelivery_is_not_newer_canonical_data` pins this current outcome, and [#196](https://github.com/zanminwang/axton/issues/196) decides whether it should change.

## P. Push

| ID | Required behavior |
| --- | --- |
| P1 | Retrying the same frozen batch with the same client ID and sequence returns its durable receipt without executing its handlers again. This relies on persisted client identity and sequence, and atomic server receipt storage. |
| P2 | The server accepts new batches in contiguous sequence order, returns cached receipts for retries, and refuses gaps or overlaps without executing them. |
| P3 | Unready prerequisites block their mutations. Lifecycle dependents wait for predecessor acceptance; sequence dependents may follow their predecessor in the same batch. Independent ready work can proceed. |
| P4 | Frozen request bytes remain unchanged across retries, restart and supported schema reconciliation. |
| P5 | Explicit rejection removes the mutation's optimism, rejects its lifecycle dependents, and retains a readable rejection until dismissed. Other pending edits replay on the remaining base. |
| P6 | A failure attributable to one mutation rolls back its savepoint, including its business changes, stamp allocations, loader readback and publications, without rolling back unrelated successful mutations. If infrastructure failure makes the enclosing transaction unusable, the delivery rolls back atomically with its receipt and can be retried; this is not rejection of all mutations. |
| P7 | A mutation-level rejection, including an unsupported mutation version, is recorded for that mutation in the receipt and retained as a client rejection (P5). It does not reject unrelated mutations merely because they share a batch. Declared lifecycle dependencies still apply; independent valid mutations can proceed. |

P5's readable rejection keeps the act as submitted - its canonical args and its Model operations with their values - as a public, stable shape, so an application can recover the author's words from it; the unsent-work streams list the refusals and the calls blocked on a failed prerequisite task account-wide and announce each commit that changes them ([#186](https://github.com/zanminwang/axton/issues/186)). Dropping an unsent call through `failures.drop` is the author's decision, not a rejection: it removes the call's optimism and keeps no refusal for it, while its lifecycle dependents are rejected and retained as P5 says. A dismissal, retry or drop made inside a local transaction is part of it (L3): later reads and calls of the transaction see it, and it commits or rolls back with the rest ([#205](https://github.com/zanminwang/axton/issues/205)). Under P3 a call that requires a task that already failed inherits the failure and waits, visibly, for an explicit retry that covers every call on the task ([#204](https://github.com/zanminwang/axton/issues/204)). Evidence: [sqlite/tests/unsent.rs](../../crates/sqlite/tests/unsent.rs), [runtime_unsent.rs](../../crates/sqlite/tests/runtime_unsent.rs).

P6 and P7 are implemented: handler rejections, loader refusals, an unsupported mutation version (`mutation_version_unsupported`), a handler failure (`handler.failed`), a loader failure (`loader.failed`) and an undeclared or unretained changed model (`model_version_unsupported`) each roll back only that mutation's savepoint and become its rejection. The only failures that still take down the whole delivery are the request envelope and authentication (`400`/`401`), client identity and order (`403 client.owner_mismatch`, `409 gap`/`overlap`), and infrastructure — a failed `rollback`, a persistence fault in `claim`, `saveReceipt`, `advanceStamp`, `ensureStamp`, a Scope operation or `scan`, or a `transaction.conflict` that retries the whole transaction. See [Server / Push](architecture/server/engine/push.md#9-architecture-decisions) and [#95](https://github.com/zanminwang/axton/issues/95).

## Q. Call outcomes

| ID | Required behavior |
| --- | --- |
| Q1 | A durable call (a Mutation by default, a Query through `enqueue`) commits canonical intent and inferred local Model operations together. It may have no Model operations; a queued Query never has any. Frozen intent bytes and call ID remain unchanged across retries and reopen. |
| Q2 | Each committed call ID has one immutable backend outcome. Claim, business writes, Loader result snapshots, stamps, Scope memberships, publications and saved response share the application transaction. A replay returns the stored outcome without re-running the handler or Loader and without allocating a stamp, a position or a membership change; no backend TTL or automatic pruning removes it. |
| Q3 | A durable call's handle reports local acceptance before backend completion. Its `wait()` resolves with either its typed result or a `CallError`; an initial local failure rejects before the handle exists. Client result objects live in memory, while queue/completion state persists. |
| Q4 | Direct calls (a Query by default, a Mutation through `call`) use a finite request/response timeout, skip durable queueing and automatic optimism, never fall back to the queue, and do not drain unrelated queued work. The direct response applies committed authority using the same stamp and pending-replay rules as a receipt. A timeout may leave execution unknown. |
| Q5 | A call's result holds only its explicitly declared outputs. A Model output is the versioned Loader snapshot, for its invocation, of the identity the handler returned, not the batch-final record authority or the current optimistic local view. An output is independent of any input with the same name and is never filled from it; a Model input alone produces no result. Nullable outputs, lists and void preserve their declared shapes. |
| Q6 | Diagnostic callback exceptions after commit cannot replace the call outcome, re-execute the handler or become transport errors; SDK runtimes report them through their uncaught-error channel. |
| Q7 | A call's authority for its caller is its input targets, always, plus the explicit Model outputs its `store` option selects (all of them by default). `store: false` changes neither the input authority nor the result. A record the handler only touched is distributed to its Scopes but is not caller authority, so the caller need not declare its Model. The policy is persisted with the durable call and is part of its call identity. |
| Q8 | A Query's settlement carries no business changes or membership declarations: one that does is rejected for that call alone, before any stamp, readback or publication, on both delivery paths and for any host. This constrains what the framework applies, not what trusted handler code can do with its own transaction. |

See [Mutations and Queries](architecture/schema/actions.md), [direct call protocol](architecture/protocol/actions.md), [server execution](architecture/server/engine/README.md) and [typed client](architecture/sdks/typed-api/client.md). Tool behavior remains [#143](https://github.com/zanminwang/axton/issues/143).

Q5 and Q7 took their current form in [#140](https://github.com/zanminwang/axton/issues/140): Model inputs no longer imply outputs, and a handler's extra changes stopped being caller authority. Evidence: [server/tests/actions.rs](../../crates/server/tests/actions.rs) `an_input_and_a_same_name_output_are_independent_and_a_missing_output_never_falls_back`, `an_extra_touch_of_an_undeclared_model_fans_out_without_caller_authority`; [server/tests/action_store.rs](../../crates/server/tests/action_store.rs) `store_false_keeps_mandatory_input_authority_and_extra_touches_never_force_storage`; end to end on both routes in [integration/action-e2e/action.test.mts](../../integration/action-e2e/action.test.mts) `an edit of A that explicitly returns B: A is reconciled, the result is B, and only A is stamped`, `a touch of a Model the caller never declared commits and reaches a different subscriber on both routes`, `a retried A-returns-B call replays its saved result without new stamps or positions on both routes`.

## T. Backend transactions

Every transaction AXTON opens on the backend runs through the `database` shim's runner ([Persistence](architecture/server/persistence.md#5-building-block-view)): a push delivery, a direct call, a Load page, a pull or live page, and `backend.transaction`.

| ID | Required behavior |
| --- | --- |
| T1 | Every such transaction is serializable: what commits is what some serial order of the committed transactions would produce. A handler or Loader needs no locks for correctness. A transaction that decides on rows another transaction reads or writes cannot commit an outcome no serial order produces; locking a parent row and then re-checking its children stays harmless but is not required. The order is some serial order, not the real-time order of commits: a transaction may be ordered before one that committed while it ran. |
| T2 | A transaction the database aborts as not serializable runs again from the start after a short random wait, up to the driver's `retries` (default 3). When they run out, the delivery fails as a server error and never as a rejection: nothing of it is saved, a durable call stays queued and is sent again, and a Load page is a `retryable` item (N5). |

**What T1 does not close.** Serializability only relates transactions that read or write the rows involved. If one transaction deletes an Author and never looks at the Author's Archives, another transaction whose snapshot predates that delete still sees the Author, writes an Archive for them and commits: the serial order "Archive, then delete" explains the result. To rule out an Archive for an Author who has left, the leaving transaction must also read or delete that Author's Archives, and then one of the two retries.

**Precondition.** A handler, Loader or `backend.transaction` body must be safe to run more than once for one call. Nothing inside it may have an external effect such as email, a push notification or an HTTP call: record the effect in the transaction and perform it after commit, the way `backend.publish` hands back a wake that the host calls after its own commit ([#180](https://github.com/zanminwang/axton/issues/180)).

A transaction the application opens itself and passes to `backend.publish` is outside T1, because AXTON does not choose its level. Its settlement is correct at Read Committed, Repeatable Read or Serializable; to get T1 for its own reads and writes, the application runs it at Serializable and retries serialization failures, as the shims do.

T1 and T2 took this form in [#202](https://github.com/zanminwang/axton/issues/202); before it the shims ran at Repeatable Read and a lock-then-recheck handler could commit a decision made on stale rows. Evidence: T1 in [driver-conformance.test.mjs](../../integration/persistence/server/driver-conformance.test.mjs) `lock-then-recheck, delete case: an Archive for an Author who already left never commits; exactly one transaction retries` and `lock-then-recheck, insert case: a delete's cleanup never misses a Star created at the same moment; exactly one transaction retries`, each run against `pg`, `prisma` and `drizzle`, with `control: at Repeatable Read both lock-then-recheck races commit on a stale re-check`. T2 end to end in [action.test.mts](../../integration/action-e2e/action.test.mts) `a Mutation whose serialization conflicts outlast the retries is a retryable failure: it stays queued and the resend commits it` (a real PostgreSQL conflict on every attempt, over HTTP to a generated TypeScript client); for Load pages, [loads.test.mjs](../../integration/persistence/server/loads.test.mjs) `transaction faults are retryable items with nothing saved, and a resend lets replay decide what committed`; the bounded, jittered retry in `a retry waits a jittered, doubling, capped delay first; the last failure and a non-retryable one are thrown at once`, `the pg driver retries only serialization failures, a bounded number of times` and `the Prisma driver retries only serialization failures, a bounded number of times, and reports the last one`. The precondition is the application's to keep: nothing checks it.

## A. Authority and settlement

Scope cursors order delivery within a subscription. Record stamps order authoritative content across every path that delivers it: a push receipt and a scope page carry the same kind of authority, compared the same way.

| ID | Required behavior |
| --- | --- |
| A1 | Delivered server values replace settled optimism; later pending edits replay over the authoritative base. |
| A2 | Within a subscription, each scope's cursor never decreases and moves only by whole pages: a page is applied as one unit and then every scope it names moves to that page's end. A scope whose range is already covered contributes nothing; a page whose range starts beyond a scope's local cursor is a gap and is not applied at all until a pull fills it, and a live frame with a gap is held, never dropped. A page answering a pull issued under an earlier subscription of the scope is stale, not a gap: it is dropped, and the registration that replaced it keeps its own position - none at all until its own first boundary is committed (D9). |
| A3 | A successful push completes from its receipt alone, after any registered local `onStore` callback and authority application commit. The receipt carries the authoritative content and stamp of every record the accepted operations targeted, read back by the framework in the handler's transaction; the client applies that authority, removes the completed operations and replays what remains in one local transaction. No scope is awaited, before or after, and a subscription is never required to complete a mutation. |
| A4 | Receipt authority is applied by the same stamp rule as page authority (D2): a newer stamp lands, an older one is ignored, an equal one with equal content rewrites nothing. Whichever arrives first, the receipt and the page for the same change leave the same state, and neither is skipped because the other already landed: a receipt whose authority the page already delivered still completes the batch, and a page whose authority the receipt already delivered still advances the cursor. |
| A5 | A receipt that cannot be applied, because it answers another client or batch, omits the authority of an accepted operation, or carries authority the client cannot decode, changes nothing. A local callback failure also commits no receipt authority or completion: the frozen batch stays for retry. A receipt for a batch already completed changes nothing either. Completion is durable and survives restart without re-sending or re-applying. |

The [client runtime](architecture/client/runtime.md#6-runtime-view) owns callback timing and failure classification; [Pull](architecture/client/engine/pull.md#6-runtime-view) owns eligible changes, and [Settlement](architecture/client/engine/settlement.md#6-runtime-view) owns frozen receipt recovery. A callback is not an observation of every local change.

A3–A5 replace the earlier checkpoint contract, under which accepted optimism waited for scope positions named by the receipt and settled in batch order ([#52](https://github.com/zanminwang/axton/issues/52), superseded by [#55](https://github.com/zanminwang/axton/issues/55)). Only one batch is in flight at a time, so completion order is send order without a separate rule. See [Settlement](architecture/client/engine/settlement.md).

## D. Distribution

Convergence assumes valid backend records, correct change and membership declarations, and eventual delivery. D7 defines isolation when an individual loader read fails on a Scope page, a receipt or a Bootstrap page; it is not the rule for native Load pages, which follow [N2](#n-native-loads). Convergence means authoritative content agrees after pending work settles; direct-only local data is outside that comparison.

| ID | Required behavior |
| --- | --- |
| D1 | Clients subscribed to the same scope converge on the authoritative records that are its members once changes stop and receipts and pages have been delivered. |
| D2 | A newer record stamp replaces authority; older content cannot regress it. Equal stamps with equal content are idempotent; conflicting equal-stamp content does not replace the stored value. Only eligible newer incoming authority invokes a registered `onStore` callback; local writes, optimism, replay and local cascades do not. A callback may run again if its transaction rolls back and delivery retries. |
| D3 | A record's stamp advances once per successful settlement that changes it, however many times the change is declared, whether or not the record belongs to any scope, and never merely to distribute a version or read an output: publishing allocates scope cursors, not stamps. Every scope the record is a member of receives that one stamp once. Adding a record with no stamp to a scope establishes one; adding an unchanged record reuses it, and adding tags to an existing member publishes nothing. Existing member → remove → re-add emits one final upsert; initially absent → add → remove emits nothing. Scope cursors advance independently of record stamps. |
| D4 | The same record identity, model read version and stamp describe the same authoritative content on every delivery path: a receipt, a pull page and the live stream. Loaders name no scope; scopes select which records are delivered, never alternate contents. A change to a record that several scopes provide reaches each of them at the same stamp, and a delayed page from any of them cannot regress a newer version. |
| D5 | A newer deletion removes the content; an older deletion cannot erase newer content. The stamp of a deleted record is retained as evidence, so older content delivered later cannot resurrect it. A parent's authoritative deletion cascades to its declared descendants locally without rewriting their stamp evidence. |
| D6 | Scope removal is synchronized release: clients merge ordered per-pair evidence, retain a replicated base held by another Scope, and evict it when the last hold is released. Release preserves stamps and pending/device-local work, cascades nothing and queues no domain write. Authoritative Loader null remains stamped absence with Model cascade rules; Loader errors remain diagnostics. Unsubscribe removes registration/progress but retains content and holding evidence. |
| D7 | A failure attributable to a loader read is reported to the application for the affected record, without invoking `onStore` for that record. A loader may throw or refuse; no durable loader-failure queue is required. Unrelated reads proceed even within the same page or scope, and the cursor still advances. Failed reads do not erase local data, become deletions, change the record's stamp or count as synchronized authority; the record is corrected the next time it is delivered. |
| D8 | Nothing a delivery cannot apply is silent. A read failure, a change the client's schema refuses, an equal-stamp conflict and a pending edit that no longer replays over new authority are each reported to the application; none of them changes local content or stamps except the divergence, which shows the authoritative base while the edit stays queued and is still sent. |
| D9 | A subscription is durable local state, registered without a connection and resumed after restart. Its origin is the first head the server acknowledges for it, committed once per subscription identity together with its delivery position; records published to the scope before that origin are not delivered by subscribing, and loading them is the separate explicit operation of D10. An uninitialized subscription has no position: it is never treated as position zero, and it is delivered to but never requested from. Later delivery moves the position only forward; a new connection is not a new origin, and an acknowledged head below a committed position is a reported fault that rewinds nothing and reinitializes nothing. Unsubscribing and registering the same scope name again is a new identity that starts over. |
| D10 | Preparing a subscription's published history is explicit, durable and bound to that subscription. It covers the scope's positions from zero to the subscription's origin whose latest retained upsert or removal positions lie in the interval when each page is read - this is compacted membership-state coverage, not a snapshot of every historical identity - and it completes only once that interval has been processed *and* ordinary delivery has reached the scope head observed when the interval finished; that head is fixed at that moment and is not refreshed while the task waits. Completion therefore means the initial publication coverage was processed under D7, not that a point-in-time snapshot was taken, not that the Scope is currently fresh, and not that every record resolved successfully: a record whose read failed is reported (D7, D8) and is corrected the next time it is delivered. A known per-record failure on a page of that interval rejects the run, keeps the successful authority and its callbacks that page did apply, does not advance the interval, and is retried only by an explicit new call, which resumes from the same committed progress. A callback failure instead rolls back that page before recording the failed run; a post-callback storage failure retains the page for local retry. A `Diverged` pending replay remains observable without failing the run. Waiting for connectivity is not failure. Unsubscribing removes the task with the registration (D6); closing the client preserves it, and reopening resumes it without a new call. |

D9 is implemented ([#150](https://github.com/zanminwang/axton/issues/150)). Evidence: the ledger and its transactions in [sqlite/tests/subscriptions.rs](../../crates/sqlite/tests/subscriptions.rs) (`set_scope_registers_without_a_boundary_and_repeats_without_a_generation_change`, `initialization_commits_waiting_rows_and_leaves_every_other_row_alone`, `a_first_boundary_survives_a_reopen_only_once_committed`, `a_head_below_a_committed_cursor_faults_and_initializes_nothing`, `an_uninitialized_subscription_is_never_read_as_cursor_zero`, `set_scope_removes_the_current_identity_and_recreation_starts_over`); the session behaviour in [sqlite/tests/downlink_worker.rs](../../crates/sqlite/tests/downlink_worker.rs) (`a_fresh_subscription_initializes_at_the_acknowledged_head_and_loads_no_history`, `an_acknowledgement_at_head_zero_initializes_at_zero`, `a_reconnect_catches_up_from_the_saved_cursor_instead_of_the_new_head`, `a_head_below_the_committed_cursor_is_a_fault_that_rewinds_nothing`, `a_recreated_subscription_starts_over_at_the_next_acknowledged_head`, `scopes_carried_through_a_rebuild_initialize_at_the_next_acknowledged_head`); and end to end against a real backend in [integration/e2e/subscriptions.test.mjs](../../integration/e2e/subscriptions.test.mjs). D6's retention through unsubscribe is asserted in the same ledger tests and in [integration/e2e/dart_live_client.dart](../../integration/e2e/dart_live_client.dart).

the public surface in [integration/bindings/client-js/subscriptions.test.mjs](../../integration/bindings/client-js/subscriptions.test.mjs) and [dart/test/subscriptions_test.dart](../../packages/dart/test/subscriptions_test.dart); and end to end against a real backend in [integration/e2e/bootstrap.test.mjs](../../integration/e2e/bootstrap.test.mjs), whose ten scenarios include the record that moves above the origin, the fixed barrier, the exact and empty intervals, an offline registration, a restart, a live read failure that completion does not rewrite, and a failed historical page with its explicit retry.

That last pair is the D7 boundary in practice: completing a load says the interval and the barrier were processed, never that a record whose read failed is now correct. Bootstrap does not discover records never added to the Scope, delete content on unsubscribe, or maintain query results. It processes retained removals as release evidence. A pair compacted above the origin belongs to ordinary delivery. Future retention ([#61](https://github.com/zanminwang/axton/issues/61)) must preserve or replace offline membership convergence before dropping log or absence evidence.

D7 and D8 are implemented for pages and receipts ([#95](https://github.com/zanminwang/axton/issues/95), [#51](https://github.com/zanminwang/axton/issues/51), [#122](https://github.com/zanminwang/axton/issues/122)). A model the client did not declare still fails the whole pull. Inside a push a loader refusal or failure is that mutation's rejection (P6). See [Server / Pull](architecture/server/engine/pull.md#9-architecture-decisions) and [Client / Pull](architecture/client/engine/pull.md).

## N. Native Loads

A native Load fills local Models in successive pages until the application backend reports completion ([Loads](architecture/schema/loads.md)). Each page is one typed read operation whose complete declared output must be applicable to count as loaded, analogous to a Query result. This is an intentional operation contract of its own: D7 does not promise atomic Load pages, and N2 does not change Scope delivery or Bootstrap.

| ID | Required behavior |
| --- | --- |
| N1 | Starting a Load commits a durable job locally, with or without a connection. Committed jobs, their frozen page requests, progress and terminal states survive reopen, and unfinished jobs resume without a new call. A Load creates no cursor or subscription, and returning a record enrolls it in no Scope; only explicit additions do (N8). |
| N2 | A page's record authority, the writes of its `onStore` callbacks, its continuation and its page count commit in one local transaction or not at all. A record the client cannot apply, an equal-stamp record with different content, a missing or unavailable record and a callback failure each roll back the whole page and fail that job; an older or equal already-known stamp with equal content is a valid no-op and still lets the page commit, and a `Diverged` replay is reported without failing it. No sibling Load shares that page's fate, even in the same HTTP batch, and no success, completion or status event precedes the commit. |
| N3 | Each page has one durable call ID and frozen request, persisted before it is sent. Reopen, transport failures, retryable items and uncertain backend commits resend the same ID, and the backend answers a repeated ID with its saved outcome (data, authority and next continuation) without running the Handler or Loader again and without allocating a stamp (Q2). Only an explicit `retry()` of a failed job replaces the call ID, reading again from the last committed continuation. |
| N4 | A response is applied only while the replica generation, job, run generation and page call ID it answers are still current. Cancel, forget, explicit retry, a pending incompatible rebuild and a rebuild make older responses inert; cancel leaves already committed pages in place. |
| N5 | Each backend page runs in its own application transaction. A terminal page failure is saved and replayed for its call ID; an infrastructure failure commits nothing and stays retryable; neither rejects a sibling item. A batch is transport grouping, never a shared database transaction. |
| N6 | Once mappings are written only by an explicit `once` start or refresh. Completion, retry and network responses never create or replace one, so work that was invalidated, or superseded by a refresh, cannot restore reuse eligibility. Cancel and forget remove a mapping only while it still names that job, and a replica rebuild drops every mapping with the jobs. |
| N7 | Completion means the backend's traversal returned no next continuation and the final page committed. It is not a snapshot, not proof the replica holds every backend row, and no record absent from a page is inferred deleted. A completed `once` hit applies no page and changes no Model. |
| N8 | A Load Handler may add, never remove, Scope membership, and only for records its page returns. The additions settle through shared settlement inside the page's savepoint: they commit with the page's saved outcome or not at all, wake subscribers only after commit, keep an existing stamp (initializing a missing one at 1), and publish each new Scope/record pair once and an existing member not at all. More than 1,000 distinct pairs or 1 MiB of them fail the page. A replayed page call ID and a completed `once` hit enroll nothing, and a replay never reverses a later removal; a fresh page re-adds idempotently. Membership outlives the Load's completion, cancellation and forgetting. Under Serializable isolation, an enrollment racing a touch of the same record either loads the newer version or the touch publishes it to the new Scope. A client whose subscription initialized before the Load receives later changes to an enrolled record through the Scope. |

Termination, enumeration consistency and read-only business behavior are the application backend's responsibility; the framework assumes nothing about successive continuation states.

## R. Resilience

| ID | Required behavior |
| --- | --- |
| R1 | Local reads and writes continue offline. Registering a subscription is one of those writes. Queued work resumes and converges when connectivity, subscriptions and backend processing recover. No delivery-time bound is promised, and nothing is promised about what a subscription requested while offline would have received before its origin (D9). |
| R2 | Dropped, duplicated, delayed and reordered messages preserve the safety properties above. Eventual convergence requires delivery to resume; permanent message loss cannot provide progress. |
| R3 | After a process interruption, durable committed sync state - subscriptions and their delivery positions included - can be reopened and resumed without losing committed work. An interruption before a first boundary commits leaves the subscription uninitialized and it initializes at the next acknowledged head; one after it resumes from the committed position. This is a recovery requirement; close/reopen tests alone do not establish arbitrary crash-boundary coverage. |
| R4 | A stale client writer cannot overwrite state committed by a newer writer generation. |

See [Testing](testing.md) for responsibility and code maps, and [Coverage review](testing/review.md) for the evidence still needed.

## Scope membership ordering and cache admission

Tags are backend-only selectors. Removing X removes the whole membership of A/X/Y as well as B/X; Y is not a retention grant. Ordered declarations settle to one final event per affected pair. A removal uses identity-only delivery and never invokes a Loader.

The local membership cursor orders evidence for one Scope/record, independently of the polling cursor and content stamp. Claims from explicit enrollment merge into this ledger without moving delivery progress. Saved replay preserves original claim cursors and performs no enrollment. A Loader diagnostic can retain positive membership evidence without replacing content.

A last-hold release records absence evidence even for untracked cache. A stale positive response may materialize only under another current hold or a request epoch at least the eviction epoch; frozen logical-request tokens survive retry and restart. This admission preserves result/continuation and queue completion. A fresh authorized one-shot read may cache again but grants no inferred membership and no general cleanup guarantee.

The 0.2 capability is a coordinated server/adapter/tooling/JS/Dart boundary. [Cutover](../../website/docs/backend/deployment.md#scope-membership-cutover) owns migration, build admission, retained legacy data and compatibility limits. Final cross-runtime verification of this boundary belongs to release acceptance; older dated test evidence above does not establish it.

## Scope declarations and coordinated cutover

Membership, label edits and selectors settle synchronously captured declarations in invocation order. Labels neither grant access nor retain a record; removing the last label leaves membership. Standalone label add requires membership and rolls back its enclosing unit when absent. Label-only edits invoke no Loader and allocate no stamp, cursor or event. A Load can add membership and labels only for returned identities; saved replay performs no effects. Predicate and label bounds are owned by the [public contract](../../website/docs/backend/api.md#select-members).

`scope-membership-v1` admission precedes handler and progress effects. The [forward migration](../../packages/postgres/migrations/2026-09-30-scopes.sql) and SQLite opening transaction preserve records, subscriptions, cursors, holds, pending/frozen work and saved outcomes, rewriting only framework metadata and claims. Application fields and opaque values remain application data. Unsupported clients cannot negotiate an old wire facade. Exact current validation evidence is recorded separately from dated historical observations.
