# Durable Load Operations Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans task-by-task. Use an Opus 5.5 implementation agent when delegated (user direction; supersedes the earlier Sol instruction); the coordinating agent owns specification review, checkpoint acceptance and final PR review. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Ship native, durable, batched Load operations that fill local Models through existing Loader and onStore contracts, resume after restart, and optionally reuse jobs with call-site once/refresh/invalidate.

**Architecture:** Separate Load descriptors, persistent jobs and a Rust Load worker reuse the existing operation-normalization, server claim/save, stamped authority, transaction callback and transport-effect infrastructure. The worker schedules bounded batches independently of Mutation sequences and Channel cursors. Each backend batch item has its own database transaction; each client page commits authority and continuation together.

**Tech Stack:** Rust compiler/core/server/client runtime, SQLite, PostgreSQL persistence, TypeScript Node/React Native carriers, Dart FFI and generated TS/Dart interfaces.

## Global constraints

- [The specification](../specs/2026-09-27-load-design.md) owns exact behavior and limits; review it before implementation.
- Base commit: `ed566eb77f9b0b47f2c128bd212261d08687e324`. Planning branch: `codex/load-operations`. Implementation worktree: `.worktrees/173-load`, branch `codex/173-load`.
- Preserve user work in other worktrees. No Oasis changes, package publication, unrelated renames or deployments.
- Keep SDKs thin. Persistence, scheduling, retries, correlation, state projection and authority acceptance are Rust responsibilities.
- A page has one durable call ID, canonical frozen request and server-replayed outcome. A batch has no shared transaction or Mutation sequence.
- State is bounded portable JSON. First/end null and `{state:null}` are distinct. Never infer completion from row count or state comparison.
- A page's store/hooks/progress are one atomic unit. No committed success until every accepted Model and hook side effect is committed. Older/same identical stamps can be skipped without failing the page.
- Initial scheduling limits: 8 items/batch, 2 client batches in flight, 4 backend item transactions concurrently, one outstanding page per job. State 64 KiB/depth 64; request 1 MiB; page outcome 1 MiB; batch response 8 MiB of page outcomes plus a 64 KiB envelope allowance; 1,000 returned identity entries/page.
- Read `docs/engineering/testing/{strategy,running}.md` and `docs/writing/README.md`. Record failures and limitations, not only test counts.
- The user-authorized [once amendment handoff](2026-09-27-load-once-handoff.md) extends this plan in flight. Incorporate its requirements into existing checkpoints; do not discard or restart completed implementation work.
- Once is opt-in and client-only: ordinary starts always create independent jobs, active once jobs are joined, completed once hits apply no Models, and invalidation cannot be undone by old completion. No backend/schema version change is required for these options.
- One PR with six sequential checkpoints. Do not advertise the feature as complete before generated SDK and real boundary tests pass.

## Checkpoint 3: Persistent jobs and atomic application

**Consumes:** stable server page identities/outcomes and existing authority `StoreDelivery` preparation/onStore/apply/commit pipeline.

**Produces:** `axton_load` and `axton_load_once` ledgers; local `start_load` with once/refresh policy, `invalidate_load`, `get_load`, `list_loads`, `cancel_load`, `retry_load`, `forget_load`; `StoreDelivery::Load` with `(replica,job,run,call)` fence; an explicit distinction between backend retry, local apply retry and terminal state.

- [ ] Add real-SQLite `crates/sqlite/tests/loads.rs` before implementation. Start offline, close/reopen, and assert canonical args/state and frozen call identity survive. Same args start distinct jobs; get reattaches by ID. Test cancel idempotence, forget only terminal jobs and retry generation behavior.
- [ ] Add the dedicated table to framework DDL and recognition, using additive creation. Store only one uncommitted page intent per job. Do not consume a Mutation ordinal, sequence, subscription ID or cursor. Bound scheduler reads and validate each ledger row independently; a corrupt named job fails visibly without blocking healthy jobs.
- [ ] Add once SQLite tests before implementation: simultaneous same-key starts produce one job; ordinary starts never read/write its mapping; complete hit and no-argument hit work offline across reopen without requesting or applying data; object key order/UUID/date normalization share a key while different args/versions/Model contracts do not. Assert failed jobs are returned without automatic retry.
- [ ] Implement the unique canonical key-to-job table with atomic lookup/create and conditional ID-based deletion/replacement. For refresh, join an active mapped job or replace a terminal mapped job with a fresh first-page job. Reject refresh without once before persistence. A failed refresh remains the mapped failure; old completed handles remain complete. Never use the Query result cache or store a second aggregate result.
- [ ] Implement normalized invalidation across retained operation/read-contract variants without cancelling/deleting the original job or Models. Only start/refresh writes a mapping. Test invalidation racing completion, a subsequent replacement completing first, and old-job retry/forget/cancel after replacement: none may restore/erase the newer mapping. Cancelled active jobs remove their own mapping, dispose never does, and cancelling complete is a no-op. Test incompatible rebuild drops all mappings and a post-rebuild once start creates fresh work.
- [ ] Add `StoreDelivery::Load` through the same owned session as authority/hooks. Test a failing hook after its local writes leaves no authority, hook writes, page count or next state committed. Mark the job failed only after rollback. An ordinary store/constraint failure has the same no-progress property.
- [ ] Test a page containing one valid and one invalid record rolls back the entire page before user callbacks. Test duplicate authority, equal-stamp divergent content, older-stamp no-op, pending optimistic rows and a later Channel update. After success, verify Model data and next/complete in the same committed snapshot.
- [ ] Test explicit retry: after a hook failure, a store failure and a committed backend rejection, `retry()` atomically increments the run generation and freezes a new call ID at the last committed continuation; committed Models/hook writes/page count stay; a late response to the old call ID is inert; `retry()` while active is idempotent and enqueues nothing; a persisting failure fails the new run again. Automatic recovery after reopen keeps the frozen call ID. Old-run waiters cannot resolve from the retry: they settle only from their own run (no `load.superseded` code, per the spec's review resolution).
- [ ] Test preparation diagnostics fail the page before hooks, `Diverged` reports do not, prepare/commit `Err` keeps the call ID for backoff, and failure diagnostics are bounded to 20 entries.
- [ ] Extend schema reconciliation: compatible reopen retains exact jobs/contracts; removed contracts fail explicitly; incompatible rebuild fences read work without delaying Mutation drain, reports abandoned IDs and invalidates existing handles with load.schema_changed; get(oldId) on the new replica returns null. No old Load rows or cursors move into the new empty replica. Add regressions in `crates/sqlite/tests/rebuild.rs`. Compatibility and rebuild code lives in `crates/client/src/lib.rs` and `crates/core/src/schema.rs`. Keep every retained Load version in the client schema; a version bump keeps in-flight jobs.
- [ ] Test the pending incompatible rebuild: with unsent Mutations on the old file, existing jobs neither dispatch nor apply and in-flight responses are inert; `start` (plain, once, refresh), `retry` and `invalidate` fail with `load.schema_pending` and create no rows or effects; `get`/`list` read the old ledger; `cancel`/`forget` work; the Mutation drain completes unchanged; the rebuild then reports abandoned IDs and old handles/waiters receive `load.schema_changed`.
- [ ] Run `cargo test -p axton-sqlite --test loads --test store_hooks --test rebuild --locked`; review and commit `feat(client): persist load progress with atomic store`.

**Review gate:** no second durable response inbox; the stable server replay is sufficient after an exit between response and local commit. No successful page advances while silently skipping a record application failure. Add the explicit native-Load page atomicity guarantee and clarify D7 remains the Channel/Bootstrap isolation rule; do not change those existing behaviors.

## Checkpoint 4: Shared worker, bounded batches and lifecycle

**Consumes:** checkpoint 3 ledger/frozen-intent/application APIs and runtime scheduler, HTTP/timer/auth-refresh effects.

**Produces:** one Rust `LoadWorker`, runtime Load command routing and observer/waiter states, a bounded request/application pipeline independent of Uplink/Downlink.

- [ ] Add `crates/sqlite/tests/load_worker.rs` and `runtime_loads.rs` with a virtual clock and captured transport effects. Nine ready jobs produce a batch of eight and one independent batch; no batch waits to fill. A job never has two pages in flight. Sixteen unconsumed outcomes prevent further request growth.
- [ ] Add `HttpRoute::Load` and a Rust per-attempt deadline timer. Load dispatch and application are lane units that alternate with push and Downlink turns (one page application per turn). Use an explicit replica generation counter for fencing.
- [ ] Implement oldest-ready selection and requeue after page commit. Park on effects without holding a writer. Integrate readiness with `runtime/tasks.rs` admission fairness; do not eagerly loop through every page in one scheduler step.
- [ ] Verify a slow Load network batch permits the second batch, a Mutation receipt, live Downlink and foreground Model reads to progress. While an `onStore` hook holds the writer, other tasks, reads included, wait, as today. A job in backoff cannot keep other ready jobs from dispatch.
- [ ] Share auth refresh, pause/resume/stop and finite attempt deadlines with runtime infrastructure. A transient refresh error backs off; only an explicit refusal is `load.unauthorized`. Persist failure attempt counts, derive capped jitter delays from injected time/entropy, preserve frozen intents across transport failures. Test mixed successful, terminal and retryable items in one response and whole-response loss after server commits.
- [ ] Add start (once/refresh options)/invalidate/get/list/status/wait/cancel/retry/forget bridge commands, status observer events and runtime fencing. Publish status after its commit and resolve wait only after final store. Close rejects waiters without cancelling durable jobs; dispose removes observers only. Stale HTTP/timer/refresh answers and cancelled callback effects must have no side effects.
- [ ] Test completed once hits create no HTTP/store effect and no Model watcher changes, while returned status observers still initialize; active joins create no duplicate scheduler item. Keep start/refresh/invalidate validation and key selection in Rust. Test a late page after invalidation may store normally but cannot recreate reuse eligibility.
- [ ] Reject management/network work, including start/refresh/invalidate, from transaction/onStore capability; retain local-only transaction APIs. Add a combined scenario with pending target schema, old Mutation drain and suspended target onStore hooks.
- [ ] Run `cargo test -p axton-sqlite --test load_worker --test runtime_loads --test runtime_lanes --test bootstrap_worker --locked` and `cargo test -p axton-binding --locked`; review and commit `feat(runtime): schedule durable load batches`.

**Review gate:** Rust owns every scheduling decision. No long-running page loop in SDK, one global HTTP lock, unbounded retained result queue or dependency on Channel initialization.

## Checkpoint 5: Generated APIs and thin SDK handles

```ts
const job = await client.loads.projectTodos({ projectId: 'p1' }, { once: true });
const stop = job.watch(status => snapshots.push(status));

stop();
job.dispose();
```

final job = await client.loads.projectTodos(projectId: 'p1', once: true);
final observer = job.watch().listen(snapshots.add);
await job.wait();
